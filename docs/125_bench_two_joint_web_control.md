# 125. 벤치 두 관절을 웹에서 움직이기 — 무엇이 막고 있었나 (2026-09-05)

> 쉬운 말로 씁니다. 우리끼리 만든 줄임말을 쓰지 않습니다. 코드 안 주석은 정확한 용어를 씁니다.

## 한 줄 결론

웹 화면에서 두 관절을 **동시에** 움직이는 데 성공했습니다. 명령한 값과 실제 값의 차이는 최대 0.40도,
흔들린 폭은 0.03도입니다. 이틀간 "화면은 멀쩡한데 모터는 안 움직인다"를 반복하게 만든 원인은
**하나가 아니라 네 개**였고, 네 개 모두 실측으로 확인해 고쳤습니다.

## 장비

| 항목 | 값 |
|---|---|
| 모터 | RS03 = 번호 3 = 엉덩이 회전 / RS04 = 번호 4 = 무릎 |
| 통신 | can0, 초당 100만 비트 |
| 로봇 컴퓨터 | 10.8.0.14 (화면은 192.168.20.177) |
| 명령 주기 | 초당 50회 (화면 → 로봇), 초당 100회 (로봇 → 모터) |

두 모터는 책상에 고정돼 있고 다리는 아직 없습니다. 그래서 아래 각도는 "관절이 몇 도"가 아니라
**모터가 켜진 순간을 0으로 본 값**입니다.

## 최종 결과 — 두 관절 동시 구동

두 관절을 **한 번의 요청에 같이** 담아 동시에 움직였습니다. 각 단계마다 12초를 기다린 뒤 쟀습니다.

| 단계 | 관절 | 명령한 값 | 자리잡은 값 | 차이 | 흔들린 폭 | 표본 수 | 기다린 시간 |
|---|---|---|---|---|---|---|---|
| 1 | 무릎 | 44.21도 | 44.08도 | −0.13도 | 0.02도 | 113개 | 12초 |
| 1 | 엉덩이 회전 | 12.21도 | 12.19도 | −0.02도 | 0.02도 | 113개 | 12초 |
| 2 | 무릎 | 54.21도 | 54.37도 | +0.16도 | 0.03도 | 112개 | 12초 |
| 2 | 엉덩이 회전 | 22.21도 | 22.23도 | +0.02도 | 0.02도 | 112개 | 12초 |
| 3 | 무릎 | 64.21도 | 64.61도 | +0.40도 | 0.02도 | 112개 | 12초 |
| 3 | 엉덩이 회전 | 32.21도 | 32.23도 | +0.02도 | 0.02도 | 112개 | 12초 |

**이 숫자로 할 수 없는 말:** 관절의 영점을 아직 잡지 않았으므로 "무릎 64.61도"는 무릎이 64.61도로
굽었다는 뜻이 아닙니다. 또 무릎에는 아직 아무 하중도 걸려 있지 않으므로, 하중이 걸린 상태의
따라가는 정확도는 이 표로 말할 수 없습니다.

원본: `/tmp/two_joint_rows.json` (세션 임시 폴더라 없어질 수 있음), 재현 절차는 아래 "다시 하려면".

## 막고 있던 것 네 가지

### 1. 힘의 세기가 관절이 스스로 버티는 힘보다 약했습니다 ★ 이번 건의 주범

같은 5도 오차를 주고 세기만 올려가며 실측했습니다.

| 세기(kp) | 엉덩이 회전(RS03) | 무릎(RS04) |
|---|---|---|
| 1.0 | +0.00도 | +0.00도 |
| 2.5 | +0.18도 | +0.02도 |
| **5.0** | **+0.31도 (요청의 6%)** | **+0.04도 (요청의 0.8%)** |
| 7.5 | +0.55도 | +1.38도 |
| 10.0 | +4.37도 | +0.66도 |
| 20.0 | +5.23도 | +5.10도 |
| 40.0 | +4.51도 | +5.45도 |

세기 5는 안전하려고 보수적으로 잡아둔 값이었는데, 재보니 **관절이 가만히 있으려는 힘조차 못 이기는
수준**이었습니다. 무릎은 명령의 0.8%만 움직였습니다. 관절이 실제로 풀리는 값은 무릎 20, 엉덩이 회전
10입니다. 벤치 상한을 **30**(감쇠 1.5)으로 올렸습니다 — RS03 정격 60, RS04 정격 120 N·m 대비
충분히 낮습니다.

**교훈:** "명령은 나가는데 안 움직인다"를 보면 통신을 의심하기 전에 **세기부터 재볼 것**.

### 2. 시작할 때 각도를 받는 대기시간이 2 ms로 고정

시작할 때 모터에게 "지금 각도가 몇이냐"고 묻고 **2 ms만** 기다립니다. 그리고 **선언한 모터 수만큼**
답이 와야 일찍 끝냅니다. 벤치는 6개를 선언하고 2개만 꽂혀 있어 6개는 절대 안 채워지므로 항상 2 ms를
다 씁니다. 그런데 명령 6개 + 응답 2개는 초당 100만 비트에서 약 0.9 ms — 2 ms 안에 들어가긴 하지만
**아슬아슬**해서 그날의 사정에 따라 갈립니다.

```
연속된 두 번의 시작, 같은 코드·같은 장비:
  2/6 motors answered   <- 성공
  0/6 motors answered   <- 실패, 그리고 영원히 회복되지 않음
```

각도를 모르면 명령을 보내지 않는 안전 규칙이 있어서, 0/6이면 그대로 끝입니다.
**모터 2개를 2개로 선언한 버스에서는 6번 연속 성공**한 것이 원인을 여기로 좁힌 결정적 근거였습니다.
답하는 모터가 더 안 늘 때까지 반복하도록 고쳤고, 지금은 `2/6 answered in 2 tries` 입니다.

### 3. 모터 전원을 켜기 전에 각도를 물었습니다

전원이 꺼진 모터는 그 질문에 답하지 않습니다. 지금까지 우연히 돌아간 건 프로그램을 **강제로 죽여서**
전원이 켜진 채 남아 있었기 때문이고, 처음으로 정상 종료를 하자 바로 재현됐습니다. 순서를 뒤집었습니다.

### 4. 온도가 100배로 보고됐습니다

온도 칸 16칸 중 **위쪽 4칸은 온도가 아니었습니다**. 관측된 세 값 `0x814A`(3309.8도) /
`0x214A`(852.2도) / `0x014A`(33.0도)의 아래 12칸이 전부 `0x14A` = 33.0도로 같습니다. 아래 12칸만
읽도록 고치니 두 모터가 36.0도, 34.0도 — 방 온도와 맞습니다. 50도 차단 장치가 이 값을 믿어야 하므로
안전과 직결됩니다.

## 배제한 것들 — 각각 실측으로

원인을 좁히는 데 쓴 검증입니다. 다음에 같은 증상을 보면 이 순서가 빠릅니다.

| 의심 | 어떻게 확인 | 결과 |
|---|---|---|
| 모터 고장 | 고장값 직접 조회 | 두 모터 다 0 — 고장 없음 |
| 전원 켜기 명령이 안 나감 | 통신선 위 프레임 캡처 | enable 두 번 확인, 끄는 명령 없음 |
| 고장 지우기가 전원 켜기를 삼킴 | 두 명령 간격을 0~400 ms로 바꿔가며 | 차이 없음 (가설 기각) |
| 명령이 로봇에 도착 안 함 | 로봇의 수신 카운터 | 1280건 수신, 거부 0건 |
| 명령 내용이 틀림 | 통신선 위 바이트 직접 해독 | 세기·감쇠·목표각 모두 정확 |
| 통신선이 죽음 | `/sys/class/net/can0/statistics` | 3초에 송신 600 / 수신 600 |

**교훈:** 추측을 쌓는 것보다 **통신선 위의 바이트를 직접 읽는 것**이 항상 빨리 끝냅니다.

## 다시 하려면

```bash
# 1. 로봇 쪽 프로그램 (10.8.0.14)
bash /tmp/start_bridge.sh <무장토큰>     # 세기 상한 30 / 감쇠 1.5

# 2. 화면에서
#    0. sync from hardware  ->  3. ARM  ->  스페이스를 누른 채 슬라이더
```

무장 토큰은 화면 프로그램의 시작 인자로 고정돼 있어 `/tx/config` 로는 못 바꿉니다. 화면 프로그램을
다시 켰다면 로봇 쪽도 그 토큰으로 다시 켜야 합니다.

## 남은 문제 (2026-09-05 시점)

1. **스페이스를 안 누른 채 슬라이더를 움직이면 화면 속 모형만 움직이고 실물은 안 움직여, 둘의 좌표가
   어긋납니다.** 하드웨어 전송이 켜진 상태에서 스페이스를 안 누르고 있으면 슬라이더를 흐리게 하고
   "지금은 못 움직입니다"를 띄워야 합니다.
2. **스페이스가 어디서는 먹고 어디서는 안 먹습니다** (누른 곳에 따라 다름).
3. **화면 위쪽 오류 숫자가 누적 전체값**이라, 이미 끝난 문제의 개수(20만 건)를 계속 보여줍니다.
   실제로 지금은 20초 동안 0건입니다.
4. 각도 표시 단위가 화면 곳곳에서 "rad"로 굳어 있는데 실제 값은 도(또는 N·m)입니다.
