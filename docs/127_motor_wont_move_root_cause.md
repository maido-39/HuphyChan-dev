# 127. "모터가 안 움직인다"가 계속 반복되는 근본 원인

작성 2026-09-07. 벤치에서 같은 증상을 일곱 번째 겪은 뒤, 사용자 지시로 개별 사례가 아니라
**공통 구조**를 분석한 기록입니다.

> 사용자 원문: *"지금 이런 모터와 연동에 관련된 오류를 한두번 겪는게 아닌데, Root Problem 이
> 뭐지? 이러면 너한테 믿고 개발을 맡길 수 없어. 공통원인 혹은 근본적인 구조적 문제가
> 무엇인지부터 분석하고, 해석해 줘."*

이 문서는 쉬운 말로 씁니다. 줄임말을 쓰지 않습니다.

---

## 1. 결론 먼저

일곱 번의 "모터가 안 움직인다"는 **일곱 개의 서로 다른 원인**이었고, **화면에서는 일곱 번
모두 똑같은 하나의 모습**이었습니다 — "표시는 전부 정상인데 모터만 가만히 있음".

원인이 구분되지 않는 이유는 하나입니다. **성공을 정의하는 값을 아무도 재고 있지 않습니다.**

우리가 화면에 띄우는 것은 전부 *부품 하나하나의 상태*입니다: 받는 속도, 보내는 속도,
무장 여부, 좌표 맞춤 여부. 각각은 자기 기준으로 정직합니다. 그런데 정작 성공을 정의하는 값,
곧 **"목표를 바꿨을 때 실측이 따라 바뀌었는가"** 는 어디에서도 계산되지 않습니다.
그 값은 양 끝을 잇는 값이고, 목표도 실측도 우리가 이미 갖고 있는데 **한 번도 비교한 적이
없습니다.** 일곱 원인 중 여섯에서 부품별 상태는 전부 정상으로 표시됩니다.

---

## 2. 이번(일곱 번째) 사건의 실제 원인

사용자는 무장까지 마치고 모터를 움직이려 했으나 움직이지 않았습니다.

### 2-1. 연결 문제가 아님 — 로봇 자신의 집계

로봇 쪽 프로그램이 자기 로그 파일에 5초마다 찍고 있던 숫자입니다
(`/home/syaro/remote_motion.log`, 로봇 10.8.0.14):

```
accepted=1722  rejected_seq=0  rejected_arm_token=0
rejected_contract=0  parse_errors=0  seq_restarts=0
```

같은 시각 뷰어가 보낸 마지막 번호는 **1723**이었습니다. 즉 **보낸 것이 하나도 빠지지 않고
전부 도착해서 전부 받아들여졌습니다.** 통신에는 아무 문제가 없었습니다.

### 2-2. 그럼 무엇이 갔는가 — 제자리 명령

| 항목 | L_hip_yaw | L_knee |
|---|---|---|
| 실제로 보낸 목표 | 0.6988 rad = **40.04°** | 0.8943 rad = **51.24°** |
| 같은 순간의 실측 | **40.2°** | **51.3°** |

**보낸 목표가 지금 있는 자리 그 자체입니다.** 1722번 동안 "그 자리에 가만히 있어라"를
보낸 것이고, 모터는 지시대로 가만히 있었습니다.

화면 콘솔에는 이 사실이 이미 떠 있었습니다:

```
L_hip_yaw_joint: 명령을 따르지 않음 (고장 의심)
  — 목표 40.2 (deg), 실측 40.2 (deg), 토크 0.01 N*m
```

**목표와 실측이 같은데 "명령을 따르지 않음 / 고장 의심"이라고 적혀 있습니다.** 오차가 0인
것은 고장이 아니라 *아무것도 명령하지 않은 것*입니다. 우리가 가진 유일한 계측기가 올바른
숫자를 보여주면서 **엉뚱한 범인을 지목**하고 있었습니다.

### 2-3. 목표가 왜 안 바뀌었나 — 겹친 두 가지

**(가) 화면 잠금이 명령을 지웁니다.**
`tools/pygviewer/pygviewer/static/dashboard.js`

- `1479`: 전송 대상 관절의 슬라이더는 **스페이스를 누르고 있지 않으면 비활성**입니다.
- `2518`: 스페이스를 떼는 순간 `/sync_from_real`을 불러 **목표를 실측 위치로 되돌립니다.**

명령을 넣을 수 있는 창은 "스페이스를 누른 채 마우스로 끄는 동안"뿐이고, 손을 떼면 방금 넣은
명령이 지워집니다. 게다가 `hwHoldState`(`1519`)는 250 ms마다 받아오는 **낡은** 하트비트
나이로 잠금을 판정하는데 기준 시간은 0.3초라, 누르고 있어도 잠금이 늦게 풀리고 중간에 다시
잠깁니다 — 브라우저는 키를 누르고 있다는 사실을 정확히 알고 있는데도 그 값을 안 씁니다.

이 잠금은 임의로 넣은 것이 아니라 사용자 지시 *"어떤때라도 그 싱크가 깨지면 안되"* 를 그대로
구현한 것입니다. 그런데 결과가 **명령을 넣을 방법이 사실상 없음**이 되었습니다.

**(나) 힘의 상한이 5로 되돌아가 있었습니다.**
뷰어를 재시작하면서 기본값(`bridge/tx_client.py:49`, `DEFAULT_KP_MAX = 5.0`)으로 복귀했습니다.
**세기 5가 이 관절의 정지마찰보다 약하다는 것은 이 벤치에서 이미 측정된 사실입니다**
(무릎에 5도를 명령했을 때 실제로 0.04도만 움직임). 풀리는 값은 무릎 20 · hip_yaw 10,
벤치 상한 30이었습니다. 위 콘솔의 **토크 0.01 N·m**이 그 증거입니다.

즉 재시작 한 번이 힘들게 찾은 값을 조용히 되돌렸고, **아무것도 그 사실을 알리지 않았습니다.**

## 3. 일곱 번의 목록과 공통 구조

| # | 실제 원인 | 화면에 보인 모습 |
|---|---|---|
| 1 | 세기 5가 정지마찰보다 약함 | 전부 정상, 모터 정지 |
| 2 | 상태 수집창 2 ms → 상태 0/6 → 가드가 스스로 영구 정지 | 전부 정상, 모터 정지 |
| 3 | 번호 게이트: 재설정 시 번호가 0부터 → 로봇이 5823개 폐기 | 전부 정상, 모터 정지 |

| 5 | 체크상자 하나에 좌표맞춤 무효화 → 무장 영구 차단 | 무장 단추만 회색 |
| 6 | Joints 탭이 `idle`에서 안 나옴 → 무장 영구 차단 | 무장 단추만 회색 |
| 7 | 목표 = 실측 (아무것도 명령되지 않음) + 세기 5 | 전부 정상, 모터 정지 |

### 3-1. 경계를 넘는 관측이 없다 *(가장 큰 구멍)*

오늘 답을 준 `accepted=1722 / rejected=0`은 **로봇이 자기 로그 파일에 찍고 있었습니다.**
조작자가 보는 화면으로 갈 길이 아예 없습니다(`bridge/huphy_remote_motion.py`의
`_StatsTicker`는 화면으로 보내지 않고 표준출력에만 씁니다). 이번 세션의 모든 진단이 사람이
원격 접속으로 그 파일을 읽어야만 가능했습니다. 제일 크고, 제일 싸게 막을 수 있는 구멍입니다.

### 3-2. 화면이 "의도"를 "상태"인 것처럼 보여준다

보낼 주소 칸이 순수한 예였습니다 — 보낼 값을 마치 설정된 값인 것처럼 보여줬습니다.
슬라이더도 같습니다: 시뮬레이터의 목표를 보여주지 실물이 어디 있는지를 보여주지 않습니다.

### 3-3. 안전장치가 사고마다 한 겹씩 늘었고, 전부 닫히는 쪽으로 실패하며, 아무도 자기가 막았다고 말하지 않는다

지금 직렬로 놓인 관문: 모드 · 설정 · 관절목록 · 전송판 · 무장 · 좌표맞춤 · 컴퓨터쪽
손떼기감지 · 로봇쪽 손떼기감지 · 무장토큰 · 번호 · 세기상한(양쪽) · 점프제한 · 범위강제.

각각은 옳습니다. 문제는 **"위험"을 고칠 때마다 "안 움직임"의 확률과 불가해성이 같이
올라갔다**는 점입니다. 조작자는 열 몇 개 중 어느 것이 닫혀 있는지 볼 방법이 없습니다.

### 3-4. 모든 설정이 양쪽에 두 벌씩 있고 대조된 적이 없다

세기 상한(뷰어 5 / 로봇 50), 관절 목록, 관절 이름표, 무장 토큰, 범위 강제 여부.
어긋나면 **더 빡빡한 쪽이 조용히 이깁니다.**

### 3-5. 진단 방법 자체의 문제 *(작성자 책임)*

추론으로 진단하고 그 추론을 사실처럼 보고한 적이 있습니다 — "구동 활성화 순서" 원인은
나중에 측정으로 반증되어 철회했습니다([[124_huphy_handoff_findings]] 끝의 "철회한 지적").
실제로 통한 방법(선 위의 바이트와 집계 숫자를 직접 읽기)은 지적을 받은 뒤에야 썼습니다.
그리고 매번 *사례*를 고치고 *계측기*는 만들지 않았습니다. 그래서 다음 고장이 똑같이
보이지 않습니다.

## 4. 만들어야 하는 것 — 명령 경로 추적

화면에 항상 떠 있는 표. 링크마다 한 줄, 각 줄에 숫자, **첫 번째 빨간 줄이 원인**입니다.
오늘 상황이었다면 이렇게 나왔어야 합니다:

```
목표가 바뀌었나   X  L_knee 51.3도 (변화 0.0도)   <- 여기서 이미 빨강
모드 manual       O
무장              O
스페이스 유지     X  마지막 6.2초 전 (기준 0.3초)
패킷 송신         O  seq 1723
로봇이 받아들임   O  1722 / 거부 0
모터가 따라옴     X  목표 40.2도 실측 40.2도 토크 0.01 N.m
                     -> 오차가 0입니다. 명령을 안 한 것이지 고장이 아닙니다.
```

**세 부분으로 나눠 만듭니다.**

1. **뷰어가 이미 가진 값만으로 되는 줄들** — 목표 대 보낸값 대 실측, 손떼기감지 나이, 모드,
   무장, 좌표맞춤, 송신 속도. 오늘 질문은 이것만으로 즉답이 됩니다. 로봇 재시작 불필요.
2. **로봇 집계를 telemetry에 실어 보내기** — `accepted`/거부 종류별/해석실패.
   `huphy_remote_motion.py`가 이미 갖고 있는 숫자를 실어 보내기만 하면 됩니다.
   **로봇 쪽 재시작이 필요하므로 사용자 확인 후 진행**([[feedback-premortem-fragile-resources]]).
3. **양쪽 설정 대조 표** — 세기 상한·관절 목록·토큰·범위 강제를 나란히 놓고 다른 칸을 표시.

### 4-1. 함께 고칠 것

- **"명령을 따르지 않음 (고장 의심)" 문구**: 목표와 실측의 차이가 0에 가까우면 고장이 아니라
  *명령이 없는 것*입니다. 두 경우를 구분해서 다르게 말해야 합니다.
- **문구가 사건 당시가 아니라 출력 시점의 값을 찍습니다.** 그래서 "따르지 않음 — 목표 40.2,
  실측 40.2"라는 자기모순 문장이 나왔습니다. 판정 당시의 값을 함께 남겨야 합니다.
- **잠금 판정을 낡은 폴링 값이 아니라 브라우저가 아는 실제 키 상태로.**
- **세기 상한을 재시작이 조용히 되돌리지 않게** — 주소와 같은 방식으로 환경변수 고정
  + 벤치에서 확인된 값보다 낮으면 화면에 경고.

### 4-2. 사용자 결정이 필요한 항목

지금의 "스페이스를 떼면 목표가 실측으로 되돌아감"은 지시 *"어떤때라도 그 싱크가 깨지면
안되"* 의 직접 구현입니다. 그런데 그 결과가 "명령을 넣을 방법이 거의 없음"입니다.

- **A안(현행 유지)**: 잠금을 그대로 두고 계측기만 붙인다.
- **B안(권고)**: 슬라이더는 항상 조작 가능하게 두고, 스페이스는 "지금 실물에 전달할지"만
  결정하며, **목표와 실측의 차이를 항상 숫자로 띄운다.** 어긋남을 막는 대신 어긋남을 항상
  보이게 하는 방식입니다.

**2026-09-07 현재 사용자 답변 대기 중.**

## 7. 후속 확인 (2026-09-07 오후): Gains 값과 속도 제한

사용자 질문 두 가지를 실물에서 확인했습니다.

### 7-1. "Gains 탭에 넣은 값이 실제로 모터 제어에 쓰이나?"

**쓰입니다. 다만 상한이 조용히 덮어씁니다.**

경로: Gains 탭 → 시뮬레이터의 kp/kd → 매 제어 주기마다 그대로 전송 →
관절마다 `kp_max`/`kd_max` 상한 적용.

상한을 30 / 1.5로 고정해 두고 Gains 값만 바꿔가며 **선 위에 실제로 실린 값**을 읽었습니다:

| Gains 탭에 입력 | 실제 나간 값 | 판정 |
|---|---|---|
| kp 12 / kd 0.6 | kp 12 / kd 0.6 | 그대로 통과 |
| kp 200 / kd 8 | **kp 30 / kd 1.5** | 상한으로 잘림 |
| kp 25 / kd 1.2 | kp 25 / kd 1.2 | 그대로 통과 |

**"바꿔도 반영이 안 된다"의 정체가 이것입니다.** Gains 값이 상한보다 크면 100으로
바꾸든 200으로 바꾸든 나가는 값은 똑같이 30입니다. 상한 아래로 내려야 그때부터
값이 달라집니다. 이제 실제 나간 값이 화면에 뜨므로 이 차이를 눈으로 구분할 수
있습니다(§4-1의 "의도가 아니라 결과를 보여준다"와 같은 원칙).

### 7-2. "속도 제한이 걸려 있나? 추종이 너무 느리다"

**걸려 있습니다. 로봇 쪽 설정 `max_delta_deg: 3.0` 입니다.**
로봇 프로그램 자신의 주석이 명시합니다: **"클리핑 = 속도 제한이다"**
(`safety/guards.py`의 `clamp_jump`).

매 제어 주기마다 명령 목표를 **현재 실측 위치에서 3도 이내로** 잘라냅니다.
결과가 두 가지입니다:

- **속도 상한** = 3도 × 100 Hz = **300 도/s** (목표가 나아갈 수 있는 최대치)
- **토크 상한** — 이쪽이 느림의 실제 원인입니다. 모터가 보는 위치 오차가 영원히
  3도를 넘지 못하므로, 낼 수 있는 힘이 `kp × 3도`로 묶입니다:

| kp | 낼 수 있는 최대 토크 |
|---|---|
| 5 | 0.26 N·m |
| 20 | 1.05 N·m |
| **30 (현재)** | **1.57 N·m** |
| 50 (로봇쪽 상한) | 2.62 N·m |

다리 관절에 1.57 N·m입니다. 목표를 아무리 멀리 줘도 모터는 3도 오차만큼의 힘밖에
쓰지 못하므로 느린 것이 당연합니다. 이 값은 커미셔닝(실측 교정) 전의 안전값으로
넣어 둔 것이며(설정 파일 주석에도 그렇게 적혀 있습니다), 바꾸려면 로봇 쪽 설정
수정과 재시작이 필요합니다. **사용자 판단 대기 중.**

## 8. 사고 기록 — 확인 작업 중 두 번의 의도하지 않은 이동

숨기지 않고 남깁니다. 둘 다 작성자가 화면을 거치지 않고 프로그램으로 직접
명령을 넣다가 발생했습니다.

### 8-1. 첫 번째 (§2-3의 상한 복구 검증 중)

**L_hip_yaw 40.1도 → 0.3도, L_knee 49.5도 → 5.8도.** 약 1초.

원인 확정: `sync from hardware`가 **목표가 아직 바뀌지 않은 상태에서 성공을
반환**했습니다. 목표 변경은 큐에 들어가 다음 제어 주기에 반영되는데, 맞춤은 즉시
"유효"로 기록됐습니다. 직접 재현:

```
실측       5.730도
맞춤 보고  5.730도로 맞췄음
실제 목표  -10.027도   <- 아직 안 바뀜
한 주기 뒤  5.730도
```

그리고 이를 막았어야 할 관문에 구멍이 있었습니다: 맞춤값과 조금이라도 다른 목표는
"의도한 명령"으로 보고 검사를 통째로 건너뛰었고, **크기 제한이 전혀 없었습니다.**
세기 상한 5로는 어떤 목표도 실행이 안 돼서 여태 드러나지 않았을 뿐입니다.

**고침(두 겹):** 맞춤이 실제 반영될 때까지 기다린 뒤 응답하고 `applied`를 보고합니다.
그리고 첫 패킷이 10도 넘게 움직일 상황이면 무장을 거부하며 관절과 이동 거리를
숫자로 말하고, 한 번 더 누르면 진행합니다. 벤치 확인: 30도 차이에서
`L_knee_joint: 5.8도 -> 35.7도, 30.0도 이동 (한도 10.0도)`로 거부.

### 8-2. 두 번째 (§7-1의 Gains 확인 중) — **원인 미확정**

**L_hip_yaw 0.25도 → −9.99도.** 약 10도.

매 회 `sync from hardware`로 목표를 실측과 같게 맞춘 뒤 무장하는 절차였으므로
움직일 이유가 없었습니다. **−10도가 어디서 온 값인지 아직 밝히지 못했습니다** —
그 관절의 기본자세(0도)도 아니고 범위 경계(±45도)도 아닙니다. §8-1에서 재현한
`-10.027도`와 값이 가깝다는 점만 관찰했고, 같은 원인인지는 **확인되지 않았습니다.**

작업 시점 상태: 무장 해제, 전송 0 Hz, 두 모터 정상, 온도 35 / 34도, 고장 없음.
무릎은 5.75도 그대로.

**하드웨어를 쓰는 확인은 여기서 중단했습니다.** 시뮬레이터만으로 −10도의 출처를
재현·확정한 뒤에 실물로 돌아가는 것이 맞습니다.

### 8-3. 이 사고들이 말해 주는 것

두 번 다 **화면을 거치지 않고** 프로그램으로 직접 명령을 넣다가 났습니다.
§4에서 만든 명령 경로 추적기의 첫 줄이 "목표가 실측과 40도 다름"을 띄우고 있었을
텐데, 작성자는 그 화면을 보지 않았습니다. 계측기를 만드는 것과 그것을 **쓰는 것**은
다른 일이며, 자동화 경로에도 같은 검사가 걸려 있어야 한다는 뜻입니다 — 그래서
10도 관문을 화면이 아니라 **서버 쪽 무장 경로**에 넣었습니다.
