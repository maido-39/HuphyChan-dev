# 126. 원격 조작·뷰어 통신 어댑터 — 무엇을 왜 어떻게 고쳤나

> **읽는 분:** 이 어댑터를 이어받거나 같이 손볼 사람
> **기간:** 2026-09-04 ~ 09-06, 책상 위 모터 2개를 실제로 돌리며
>
> 쉬운 말로 씁니다. 저희끼리 만든 줄임말을 쓰지 않습니다.
> 항목마다 **무엇이 / 왜 문제이고 / 어디이고 / 어떻게 고쳤는지**를 코드와 함께 적었습니다.

## 이 문서에 없는 것

**HUPHY 본체 이야기는 여기 없습니다.** 그건 [`docs/124`](124_huphy_handoff_findings.md) 에
따로 있습니다. 이 문서는 **저희가 만든 통신 어댑터**에서 찾아 고친 것만 담습니다.

## 이 어댑터가 무엇인가

브라우저에서 슬라이더를 끌면 책상 위 모터가 도는 길입니다. 프로그램은 셋뿐입니다.

| 어디 | 무엇 | 파일 |
|---|---|---|
| 내 컴퓨터 | 화면·시뮬레이터·명령 생성 | `tools/pygviewer/pygviewer/` |
| 내 컴퓨터 | 로봇이 보낸 자료를 화면에 밀어 넣음 | `bridge/huphy_udp_forward.py` |
| 로봇 컴퓨터 | 명령을 모터 말로 바꿔 초당 100회 보냄 | `bridge/huphy_remote_motion.py` |

```
슬라이더 → 화면 프로그램 → UDP 9872 → 로봇 프로그램 → CAN → 모터
모터 → CAN → 로봇 프로그램 → UDP 9870 → 중계기 → 웹소켓 → 화면
```

전체 구조와 조작 순서는 별도 안내서에 그림으로 있습니다(세션 산출물, `docs/121` 참조).

# 1부 — 명령이 조용히 사라지던 것들

이 부의 세 가지는 성격이 같습니다. **아무 오류도 안 뜨는데 모터만 안 움직입니다.**
통신·제어 주기·화면 표시가 전부 정상으로 보입니다. 그래서 찾는 데 가장 오래 걸렸습니다.

## 1-1. ★★★ 전송을 다시 설정하면 로봇이 모든 명령을 무시합니다

### 무엇이

로봇은 메시지마다 붙은 **일련번호**가 지금까지 받은 것보다 낮으면 버립니다. 순서가 뒤바뀐
패킷을 걸러내려는 장치입니다.

그런데 화면 쪽은 `/tx/config`(전송 재설정)를 부를 때마다 보내는 객체를 **새로 만들고**,
새 객체의 번호는 **0부터** 시작합니다.

### 왜 문제인가

로봇은 이전 번호를 기억하므로 그 아래는 전부 버립니다. 초당 50회로 보내니, 예전 번호가
6000이었다면 **2분 동안 아무것도 안 듣습니다.**

```
실측:  accepted=843     rejected_seq=5823
       -> 게인 4단계를 재는 실험이 145초 내내 통째로 아무것도 안 하고 끝남
```

그 실험은 "네 게인 모두 오차 0.00도"라는 **깨끗해 보이는 결과**를 냈는데,
**아무것도 안 움직인 결과**였습니다.

### 어디 / 어떻게

`tools/pygviewer/pygviewer/tx.py::configure` — 새 객체에 **이전 번호를 이어받게** 합니다.

```python
    resume_seq = 0
    if self._client is not None:
      last = self._client.last_seq
      resume_seq = 0 if last is None else last + 1
      self._client.stop()
    ...
    self._client = TxClient(..., start_seq=resume_seq)
```

`bridge/tx_client.py` 에 `start_seq` 인자를 추가했습니다.

### 화면을 아예 다시 켜면? — 로봇 쪽에서 알아보게

새 프로세스는 번호가 **진짜 0부터**라 위 방법으로 못 막습니다. 로봇이 스스로 알아보게 했습니다.

`bridge/remote_target.py::LatestOnly.put`

```python
  SEQ_RESTART_RUN = 50
  """낮은 번호가 끊기지 않고 이 횟수만큼 이어지면 "송신자가 다시 시작한 것"으로 본다.

  50은 초당 50회에서 1초. 순서 뒤바뀜은 한두 개이고 다음 정상 패킷이 바로 끊으므로
  이만큼 이어지지 않는다. 반대로 화면을 다시 켠 사람이 죽은 로봇을 붙들고
  영문을 모른 채 기다리지 않을 만큼은 짧다."""
```

순서 뒤바뀜과 구별하는 근거는 **길이와 증가 여부**입니다. 뒤바뀜은 한두 개이고 다음 정상
패킷이 끊습니다. 다시 시작한 송신자는 낮은 번호가 **끊기지 않고 계속 올라옵니다.**

### 실기 확인

```
재설정 5회      -> 5/5 따라옴, 순번거부 +0        (고치기 전에는 수천 건)
화면 완전 재시작 -> 3/3 따라옴, 첫 회만 39건 버린 뒤 1초 안에 자동 복구
```

로봇 기록에 `seq_restarts` 항목과 "송신자가 번호를 다시 시작했다"는 경고를 남깁니다.

## 1-2. ★★★ 무장 암호를 켤 때마다 새로 만듭니다

### 무엇이

화면 프로그램이 시작할 때마다 무장 암호를 **무작위로** 만듭니다.

```python
# tools/pygviewer/pygviewer/tx.py:96 (고치기 전)
self.arm_token = secrets.token_hex(8)
```

### 왜 문제인가

로봇은 시작할 때 받은 암호를 계속 검사합니다. 그래서 **화면만 다시 켜면 로봇이 전부
거부**하고, 역시 아무 표시도 없습니다. 하루에 두 번 겪었습니다.

### 어디 / 어떻게

같은 파일. 환경변수로 고정할 수 있게 했습니다.

```python
    env_token = (os.environ.get("PYG_ARM_TOKEN") or "").strip()
    if env_token:
      self.arm_token = env_token
      self.arm_token_pinned = True
    else:
      self.arm_token = secrets.token_hex(8)
      self.arm_token_pinned = False
```

```bash
PYG_ARM_TOKEN=<암호> python3 tools/pygviewer/run.py --variant LegOnly-AB ...
```

**빈 값은 무작위로 처리합니다** — 빈 암호가 우연히 맞아 버리는 일을 막기 위해서입니다.
고정은 양쪽을 다 관리하는 사람만 쓰십시오. 여전히 공유 비밀이라 기록에 남기면 안 됩니다.

## 1-3. ★★ 시작할 때 각도를 한 번만 물어, 간헐적으로 영구 정지

### 무엇이

HUPHY 는 각도를 모르는 모터에 명령을 보내지 않고, 각도는 명령의 응답으로만 옵니다
(`docs/124` 2-3). 그래서 시작할 때 한 번 받아 둬야 하는데, **한 번만** 물었습니다.

### 왜 문제인가

받는 창이 2 ms 고정이라(`docs/124` 1-4) 간헐적으로 0개를 받습니다. 0개면 그대로 영구 정지고,
루프는 100 Hz 로 멀쩡히 도는 것처럼 보입니다.

### 어디 / 어떻게

`bridge/huphy_remote_motion.py` — 답하는 모터가 **더 안 늘 때까지** 반복합니다.

```python
  SEED_DEADLINE_S, SEED_GAP_S = 1.0, 0.02
  ...
    while time.monotonic() < deadline:
      missing = set(bus_obj.refresh_states() or ())
      grew = {m for m in ids if m not in missing} - answered
      answered |= grew
      if answered and not grew:
        break          # 한 번 더 물어봐도 새로 답한 모터가 없으면 그게 전부
      time.sleep(SEED_GAP_S)
```

없는 모터(1·2·5·6번)는 영원히 답하지 않으므로 "전부 답할 때까지"가 아니라
**"더 안 늘 때까지"** 입니다. 실측: `2/6 answered in 2 tries`.

토크를 켜는 것도 이 앞으로 옮겼습니다. 다만 **그 이유는 정정했습니다** —
꺼진 모터도 명령에 답한다는 것을 나중에 실측으로 확인했습니다(`docs/124` 철회 항목).
순서상 자연스럽고 해롭지 않아 그대로 두었을 뿐입니다.

# 2부 — 안전장치

## 2-1. ★★★ ±180도 감김을 막는 장치 (신설)

### 무엇이

관절이 한 바퀴 넘게 감기면 접힌 각도가 평범해 보이는데 실제 위치는 전혀 다릅니다
(근본 원인은 HUPHY 쪽, `docs/124` 1-1). **막는 장치가 아무 데도 없었습니다.**

### 어디 / 어떻게

`bridge/motor_fault.py::WrapGuard` (신설). 원시 각도를 보고 판단합니다.

| 원시 각도 | 상태 | 동작 |
|---|---|---|
| 150도 미만 | 정상 | — |
| 150~170도 | 주의 | "되감는 것이 좋습니다" |
| 170도 초과 | 차단 | 그 관절에 명령을 보내지 않음 |
| 한 주기에 180도 이상 튐 | 차단(고정) | 실제로 접힘. 사람이 되감고 풀어 주기 전까지 유지 |

마지막 줄이 중요합니다 — 한 번 접히면 **같은 숫자가 두 개의 다른 물리적 위치**를 뜻하고
전선 위에서는 구별이 안 됩니다. 그래서 스스로 풀리지 않게 했습니다.

```python
WRAP_JUMP_WINDOW_S = 0.5
"""이 시간보다 멀리 떨어진 두 관측은 접힘 판정에 쓰지 않는다.

튀었다는 것이 접힘을 뜻하려면 두 관측이 **연속**이어야 한다. 시간이 떨어진 표본은
아무 말도 못 한다 -- 그 사이에 관절이 갈 시간이 있었거나, 모터가 조용했다 돌아온 것이다."""
```

이 시간 조건은 **시험이 잡아낸 설계 결함**입니다. 첫 판은 시간이 떨어진 두 관측을 나란히
놓고 "접혔다"고 오판했습니다(모터가 잠시 조용했다 돌아오면 헛발동).

### 검증 방식에 대해

발동 경로는 **시험 코드로** 증명했고(`tests/test_wrap_guard.py`, 10건),
**실제 모터를 ±180도로 몰지 않았습니다.** 그건 장비를 망가뜨린 사고를 일부러 재현하는
일이고 복구에 몇 시간이 걸렸습니다. 실기에서는 **평소 동작을 방해하지 않는지**를 확인했습니다 —
정상 구동 2/2, 헛발동 0건.

## 2-2. ★★ 과열 차단 — 그리고 모터를 달구지 않고 시험하는 방법

### 무엇이

50도에 닿으면 그 관절의 힘을 끊고 45도 아래로 식으면 다시 시작합니다
(`bridge/motor_fault.py::ThermalCutoff`). 만들어 두고 **한 번도 발동시켜 본 적이 없었습니다.**

### 어디 / 어떻게

기준값을 밖에서 **낮출 수만** 있게 했습니다.

```python
def _env_float(name: str, default: float) -> float:
    """...차단은 모터를 보호하려고 있으므로 잘못된 값으로 **올라가면 안 되고**
    오타로 조용히 없어져도 안 된다 -- 이상한 값은 제한 해제가 아니라 기본값으로 되돌린다."""
    ...
    if not (0.0 < v <= default):
        logger.warning("%s=%.1f is outside (0, %.1f] - keeping %.1f", name, v, default, default)
        return default

OVERHEAT_CUTOFF_C = _env_float("PYG_OVERHEAT_C", 50.0)
OVERHEAT_RESUME_C = OVERHEAT_CUTOFF_C - 5.0
```

99를 넣으면 50이 유지됩니다.

### 실기 확인

```
기준 36도 · 엉덩이 회전 37.0도 / 무릎 35.0도
  WARNING  hip_yaw: 과열로 힘을 끊음 (온도 37.0도, 기준 36도)
  같은 +8도 명령 -> 엉덩이 +0.00도 (차단)   무릎 +7.71도 (정상)
기준 50도로 복귀
  INFO  L_hip_yaw_joint: 식어서 다시 시작 (온도 37.0도)
```

끊는 쪽과 되살리는 쪽 **둘 다** 실기에서 확인했습니다.

## 2-3. ★★ 고장을 '상태'가 아니라 '사건'으로 기록하기

### 무엇이

로봇 텔레메트리는 각 항목의 마지막 값을 계속 들고 있습니다. 그래서 **안 바뀐 고장값이
패킷마다** 도착하는데, 그걸 매번 새 사건으로 적고 있었습니다.

### 왜 문제인가

```
25초에 10,516건  (초당 420건), 누적 1,129만 건
전부 연결조차 안 된 모터(hip_pitch, hip_roll) 것
```

값 자체도 2-4의 고장 조회를 잠깐 켰을 때 **없는 모터에서 읽은 쓰레기**였습니다.
**진짜 고장이 나도 저 홍수 속의 한 줄이 됩니다.** 고장을 보이게 만들려던 기능이 정확히
반대 일을 하고 있었습니다.

### 어디 / 어떻게

`pygviewer/telemetry.py:231` — **바뀔 때만** 기록합니다.

```python
        if fault_le is not None:
          changed = self.fault_le[n] != fault_le
          self.fault_le[n] = fault_le
          ...
          if fault_le != 0 and changed and self.violations is not None:
```

처음 뜰 때, 다른 고장으로 바뀔 때, 사라졌다 다시 뜰 때만 적힙니다.
`rate_limit_s` 는 **보이는 목록만** 얇게 만들 뿐 누적 숫자와 콘솔은 전속력으로 돌고 있었습니다.

**실측: 25초에 10,516건 → 0건.** 시험 5건(`tests/test_fault_event.py`).

## 2-4. ★★ 고장값을 밖에서 물어보면 각도가 망가집니다 → 기본 꺼짐

### 무엇이

HUPHY 가 고장값을 안 실어 줘서(`docs/124` 1-5) **별도 소켓으로 직접 물어보는 우회**를
만들었습니다. 처음 동작한 지 1분 만에 껐습니다.

### 왜 문제인가

```
켬:  무릎 각도가 39.90도와 −0.21도 사이를 오감 — 148표본 중 18개가 가짜 0도
끔:  39.88 ~ 39.90도, 폭 0.02도 — 가짜 0도 0/148
```

고장 응답과 상태 응답은 CAN 번호가 같아 구분이 안 되고, socketcan 은 모든 소켓에 프레임을
뿌립니다. 그래서 저희 조회의 **답장을 HUPHY 버스가 상태값으로 해독**합니다.
가짜 0도 기준으로 계산된 명령은 40도 이동이 됩니다.

### 어디 / 어떻게

`bridge/huphy_remote_motion.py::_make_can_fault_query_fn` — 기본 꺼짐으로 되돌렸습니다.

```python
  if os.environ.get("PYG_FAULT_POLL", "").strip() not in ("1", "true", "yes"):
    logger.warning(
      "remote_motion: fault code reading is OFF by default - polling it from a second socket "
      "corrupts the state stream (docs/125 round 3). Set PYG_FAULT_POLL=1 to override."
    )
    ...
    return None
```

제대로 된 해결은 HUPHY 쪽에서 내보내 주는 것입니다(`docs/124` 1-5).

# 3부 — 조용히 죽어 있던 것들

## 3-1. ★★ 모터와 이름을 객체 동일성으로 짝지었습니다

### 무엇이

모터 번호와 이름을 짝지을 때 **객체가 같은지**로 비교했습니다.

```python
# 고치기 전 — 두 사전은 값은 같지만 서로 다른 객체라 한 번도 안 맞음
cfg_to_name = {id(cfg): name for name, cfg in leg.config.motors.items()}
name_by_id = {mid: cfg_to_name.get(id(cfg)) for mid, cfg in limb_cfg.motors_by_id().items()}
```

### 왜 문제인가

한 번도 안 맞아서 **두 기능이 조용히 꺼져 있었습니다** — 고장값 읽기는 하루 종일,
감김 감시는 붙이자마자. 시작할 때 경고 한 줄만 남는데, "아직 배선 안 됐나 보다"로 읽히기
쉽습니다. **고장을 보이게 하려는 기능이 안 보이게 실패하는 것**이 가장 나쁜 형태입니다.

### 어디 / 어떻게

`bridge/huphy_remote_motion.py` — 모터가 들고 있는 **번호**로 짝짓습니다.

```python
    name_by_id = {int(cfg.id): name for name, cfg in leg.config.motors.items()
                  if getattr(cfg, "id", None) is not None}
```

고친 뒤: `fold guard active for [...]`, `fault code reading enabled ...`.

---

## 3-2. ★ 관측값을 `.tau` 로 읽어 항상 비어 있었습니다

HUPHY 는 통신 항목에는 `tau`, 관측 사전에는 `.torque` 를 씁니다(`docs/124` 4-1).
저희는 `.tau` 로 읽었고 **아무 오류 없이 항상 비어 있는 값**을 받았습니다.

```python
# bridge/huphy_remote_motion.py
OBS_POS_SUFFIX = ".pos"
OBS_TAU_SUFFIX = ".torque"   # was ".tau" - HUPHY writes ".torque" (robots/leg.py:366)
OBS_TEMP_SUFFIX = ".temp"
```

이것 때문에 "명령을 안 따른다" 감지기가 한 번도 발동하지 않았습니다.

## 3-3. ★ 자세 센서 자료를 받고도 버렸습니다

중계기가 **모든 패킷을 관절 해석기로** 넘겼습니다. 자세 패킷에는 관절 값이 하나도 없어서
해석기가 "새 게 없음"을 뜻하는 빈 값을 돌려주고, 그대로 버려졌습니다.

```python
# bridge/huphy_udp_forward.py
          js = (bridge.parse_imu(payload) if any(k.startswith("imu/") for k in payload)
                else bridge.parse_fast(payload))
```

해석기 자체는 이미 잘 만들어져 있었습니다(`bridge/huphy_udp.py::parse_imu`) — 부르는 곳이
없었을 뿐입니다. 고친 뒤 실측: 중력 크기 1.003, 가속도 크기 9.823 m/s²(중력가속도 9.807),
정지 상태 각속도 0.00, 화면 도달 0.010초.

# 4부 — 화면

## 4-1. ★★ 스페이스를 안 눌러도 화면 속 모형만 움직였습니다

### 무엇이

전송이 켜져 있어도 스페이스를 안 누르면 실물은 안 움직이는데, **슬라이더는 그대로 먹혀서**
화면 속 모형만 움직였습니다. 둘의 좌표가 어긋납니다.

### 어디 / 어떻게

`static/dashboard.js::hwHoldState` (순수 함수). 명령이 실물에 닿을 수 없는 상태면 해당 관절
슬라이더를 **흐리게 하고 잠급니다.**

- 전송은 켜졌는데 무장 전
- 무장했는데 스페이스를 안 누름

잠긴 슬라이더는 스스로 아무 신호도 못 내므로, **줄 전체가 눌림을 받아** 왜 못 움직이는지
알려 줍니다. 그리고 손을 떼는 순간 **화면 값을 실물 값에 다시 맞춥니다** — 둘이 갈라질 수
있는 마지막 순간입니다.

## 4-2. ★★ 스페이스가 슬라이더에 먹혔습니다

글자를 입력하는 칸인지 판단하는 코드가 `<input>` 이면 전부 "입력 중"으로 봤는데,
**슬라이더가 바로 `<input type="range">`** 입니다. 그래서 슬라이더를 한 번 만지면
그 순간부터 스페이스가 죽었습니다 — 정작 필요한 순간에.

```js
const TEXT_INPUT_TYPES = new Set([
  "text", "number", "password", "email", "search", "url", "tel",
  "date", "time", "datetime-local", "month", "week",
]);
```

키 감지는 `window` 의 **캡처 단계**로 옮겨, 3D 화면이나 다른 요소가 가로챌 수 없게 했습니다.

## 4-3. ★ 이상값 경보가 누적 전체값이고 단위가 틀렸습니다

숫자가 **누적**이라 이미 끝난 문제 20만 건을 몇 시간째 붉게 보여 줬습니다(그 시점 실제로는
20초 동안 0건). 그리고 모든 값에 "rad" 를 붙여, 60 N·m 짜리 힘 포화를 `60.000 rad` 라고
썼습니다.

이제 **최근 60초 건수**를 앞세우고, 지금 아무 일도 없으면 붉은색을 벗으며, 단위를 항목에
맞게 도 또는 N·m 로 적습니다.

## 4-4. ★ 왼쪽 탭이 "내가 그렸다"를 안 남겨 화면이 터졌습니다

각 탭은 `body.dataset.builtTab` 에 자기 이름을 남겨야 합니다. 안 남기면 **다음에 원래 탭으로
돌아갈 때 이미 그려졌다고 착각하고** 사라진 요소를 만집니다.

```
04:04:09.324 [JS ERROR] renderLeftTab: can't access property "textContent", el(...) is null (x18)
```

새 탭이 빠뜨려 터졌고, 고치면서 보니 `Model`·`Status` 탭도 **원래부터** 안 남기고 있었습니다.
셋 다 고치고, 기본 탭과 화면에 선택 표시된 탭이 어긋나 있던 것도 맞췄습니다.
시험으로 묶어 다음에 탭을 추가할 때 같은 실수를 못 하게 했습니다
(`tests/test_left_tab_stamp.py`).

## 4-5. 지금 무엇을 하는 중인지 이름 붙이기

세 축(화면 모드 / 전송 무장 / 로봇 프로그램)이 정해진 조합과 **정확히** 맞을 때만 이름이
붙고, 하나라도 어긋나면 이름을 떼고 무엇이 다른지 지목합니다(`pygviewer/scenario.py`).

셋 중 **로봇 프로그램**만 화면이 알 방법이 없었습니다. 로봇 프로그램이 자기 번호를 진단
패킷마다 실어 보내게 해서 **믿는 것에서 아는 것으로** 바꿨습니다. 2초만 조용해도 다시
"모름"으로 떨어집니다.

버튼은 화면이 가진 축만 바꾸고 **무장은 하지 않습니다** — 실물에 힘이 들어가는 조합에
가는 길(값 맞추기 → 무장 → 스페이스)은 그대로여야 하기 때문입니다.
