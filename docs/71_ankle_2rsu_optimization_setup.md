# 71. Ankle 2-RSU 치수 최적화 — 문제 정의 (2026-08-04)

> [!danger] ★★★★★ 2026-08-13: 박스+swing_foot 한도 20°가 실사용 자세와 구조적으로 안 맞음 — §8/§9 전체 폐기, §10이 현재 유일한 신뢰 결론
> §8g~§9j(pitch 부호 negate 패치)까지 나온 모든 수치·기하·그래프·애니메이션(v3c, v5a/b/c 포함)는 **폐기**. 처음부터 로봇 MJCF 관절체인에서 회전행렬을 재유도하고(§10a, FK로 pitch+roll 동시자세 검증) 2-RSU 기구학을 다시 세운 결과(§10b), swing_foot 계산식 자체에 **별도의 독립적인 여각(90°−진짜각) 버그**가 있었다는 것도 발견(§10c). 두 버그를 모두 고친 뒤:
> - 확정 박스(A_r/B_r 40~65·RP_B 50~75·RP_r 35~50·A_h 35~45·B2RP 170~200·RP_h −10~10)로는 ROM 전역(pitch −50~+30°·roll ±20°)에서 **swing_foot≤20°가 성립하지 않는다**(최악 ~54°, §10f).
> - **실측 replay(13,503샘플) 기준으로는 더 심각 — 99.1%가 20° 한도를 초과, 중앙값 39.7°**(§10g).
> - ROM의 방향(부호) 자체는 맞게 걸려 있다 — 문제는 방향이 아니라 이 배치가 요구하는 요동각 크기.
> - **사용자 결정 대기 중**: 박스 하한 완화 / B2RP 상한 완화 / SWL_F 완화 / 배치 재설계 중 최소 하나 필요(§10f 끝).
>
> 아래 §8~§9는 진행 기록으로만 남기고(감사 과정 투명성 목적), **결론은 §10을 따를 것**.

목적: 실측 하중 데이터(§64 §10, fc/fcp)를 수요로 물려 **발목 2-RSU 기하 10파라미터의 최적 치수**를 뽑는다. 파라미터는 3계층으로 나눈다(사용자 지시). 방법론은 [[60_fourbar_optimizer_research]]의 확정 원칙(Deb 3규칙 — **hard 제약과 목적을 절대 합성하지 않는다**)을 따른다.

## 목적함수 (제안 — 확인 요망)

hard 제약 통과해(feasible) 중에서, **여유의 최소값을 최대화** (minmax margin):

$$\max_{\theta \in \text{feasible}} \; \min\!\Big( \underbrace{1-\frac{\tau_{mot}^{P99} \cdot 1.25}{60}}_{모터토크}, \; \underbrace{1-\frac{(\omega,\tau)_{TN\text{초과율}}}{1}}_{TN곡선}, \; \underbrace{1-\frac{f_{rod}^{P99} \cdot 1.25 \cdot 1.5}{C0}}_{로드엔드}, \; \underbrace{1-\frac{요동각}{13°}}_{요동} \Big)$$

동률이면 2차 기준: 로드축력 RMS 최소(짐벌·로드엔드 마모) → 크랭크 스윕부피 최소(패키징). 페널티 합성 금지(Deb), DE/rand/1/bin 또는 3변수라 **전수 그리드(2~5 mm 스텝)**도 가능 — 그리드 권장(재현성).

1. **T-N 제약은 모터링 사분면(τ·ω>0)만** — 발목 관통 이벤트(§8k)는 지면이 모터를 역구동하는 것이라 제외. 포함하면 전 설계가 infeasible(-800%)이 되는 인공물. T-N은 실측 무릎형(60 N·m 유지 → 12.6 rad/s 무릎 → 19.8 무부하, RS03_TN_curve_48V.csv).
2. **raw peak(클립 90 N·m·단발)는 hard 제약에서 제외** — P99×1.25가 hard, peak는 초과빈도 리포트 전용(§65 doctrine). 로드엔드만 peak ≤ C0 유지(브리넬).

### §6b 파라미터 수렴 방향 시각화 + "모터당 31 N·m" 검증 (2026-08-04)

![funnel](mujoco/assets/ankle_opt_param_funnel.png)

**"31.2 N·m이 너무 낮다(실측은 한참 넘는다)" 검증 결과 — 데이터 누락 아님, 분담 구조가 원인**:
- 수요 데이터에 rough 포함 확인: 관절 τ_pitch P99 flat 53.9 / rough 48.9 / pooled 52.0 N·m — §7 계열 표와 일치.

- **정직한 캐비앗**: 모터당 raw peak 80.8 N·m > 60 — **초과 빈도 0.022%(≈2회/h)**, 전부 sim 자체 클립(관절 90) 순간. doctrine상 P99×1.25=39≤60으로 통과, 초과 순간은 실기에서 짧은 포화(추종 순간 손실)로 나타남.

## §7 ★IK 브랜치 버그 발견·수정 — §5·§6·§6b 결과 전면 대체 (2026-08-04)

사용자 의심("기구학 제대로 풀었나?")에 따른 3중 검증에서 **IK 해집합 버그 발견**: φ = β ± acos(k/ρ)가 정답인데 π+β±d(부호반전 해)를 풀고 있었다. 폐합 잔차 최대 110 mm. 파워밸런스 검증(1e-14)은 "잘못된 맵의 내적 일관성"만 봐서 통과했던 것 — **에너지 검증만으로는 기구학 검증이 안 된다**는 교훈. 브루트포스 500/500으로 신공식 확정, 설계기·최적화기 모두 수정. 수정 후 3중 검증: 폐합 1e-13 ✓ · 파워 1e-14 ✓ · **독립 경로(J^-T vs UJ 모멘트평형 직접해) — 로드력 크기 4.6e-7 일치 ✓**(부호는 두 검증 루트의 인장/압축 규약 차이로 로드별 상이 — 마진은 전부 |f| 기반이라 무영향. 단 ★로드 좌굴 체크는 압축 부호 확정 후 별도 필요: Ø6 강봉 L330 기준 Euler ~1.2 kN vs peak ~2 kN — **로드 몸통 지름 8 이상 권장, 추후 확정**).

### §8d 수렴 강건성·local minima 검토 (진행 중, 2026-08-12)

사용자 지적 2건에 대한 조사: ①패턴서치가 iteration cap(120)에 그냥 걸리는 건지 진짜 수렴인지, ②여러 시작점이 진짜 같은 곳으로 수렴하는지(local minima 회피).

**중간 관찰(30-멀티스타트, iter cap 50, 262144박스 재현)**: feasible 종점 score가 **0.2%~3.1%로 넓게 흩어짐**(같은 박스에서 앞서 나온 3.5~3.7%보다 낮은 값들 다수) — 전부 iteration cap(50)에서 잘림. **사용자 의심이 근거있다** — 조기절단·local minima 둘 다 배제 못함.

**진행 중인 진단**: 기존 시드들을 종점에서 이어받아 iteration cap을 400까지 늘려 매 iteration마다 score를 기록하는 딥다이브(최악/중간/최선/infeasible 대표 시드) + 새 멀티스타트 30개(iter cap 200)를 **3개 프로세스 병렬**로 재실행 중(메모리 15GB로 증설 확인 후). 목적: score가 iteration을 늘려도 계속 오르는지(=조기절단 문제, 처방=cap 상향) vs 낮은 값에서 평평해지는지(=진짜 다른 local minimum, 처방=global 탐색 강화 필요).

⚠️ **작업 중 발생한 사고 2건(교훈으로 기록)**:
1. 첫 백그라운드 실행을 `python3 ... | tail -100`으로 걸었는데, `tail`이 `-f` 없이는 **입력 EOF까지 아무것도 안 흘려보내는** 구조라 90분 넘게 진행상황을 전혀 못 봄 — 프로세스를 강제종료해서야 버퍼링된 로그를 확인. **교훈: 백그라운드 장시간 작업은 파이프 없이 직접 리다이렉트하거나 `tail -f`를 쓸 것.**
2. 메모리 7.7GB 환경에서 2개 프로세스를 동시에 돌렸다가 OOM으로 하나가 죽었고, 곧이어 **환경 자체가 재시작**되어 `/tmp` 스크래치패드와 실행 중이던 모든 백그라운드 프로세스가 소실(저장소 파일은 무사). 재시작 후 메모리가 15GB로 증설된 것을 확인하고 재작업.

### §8d 결과 — ★진짜 local minima로 확인됨 (가설 정정) (2026-08-12)

3개 프로세스 병렬(각 10개 다양한 Sobol 시작점, iteration cap 200, 매 iteration 점수 기록) — **총 30개 완주**(16 feasible·14 infeasible). 도중 세운 "같은 basin, 수렴 깊이만 다름" 가설은 **아래 데이터로 반박·정정됨**.

![convergence_trace](mujoco/assets/convergence_trace_score_vs_iter.png)

**결정적 관찰**:
1. **iteration 캡은 원인이 아니다** — 16개 feasible 시드 전부 **iteration ~10 부근에서 완전히 평평(dead flat)**해진다. 마지막 50회(iter 150→200) 동안 점수 변화는 16개 전부 **정확히 0.0pp** — 200까지 늘려도 더 나아지지 않는다(50이든 120이든 200이든 결론 동일, 종료조건이 peakScore/fRMS 같은 2차 기준의 미세한 흔들림 때문에 늦게 걸릴 뿐, 1차 지표인 P99 score는 훨씬 일찍 정지함).
2. **★진짜 local minima다** — 평평해진 최종값이 시드마다 다르다: **0.47% ~ 3.38%**(중앙값 ≈2.99%), 서로 겹치지 않는 뚜렷이 분리된 수평선. 파라미터 클러스터링(§6과 동일한 정규화거리 0.28 기준)도 **16개 feasible 시드 = 16개의 서로 다른 클러스터**(단 하나도 병합 안 됨) — 좌표하강 패턴서치가 시작점 근방의 국소해에 그대로 갇힌다는 뜻.

**PCA 시각화(9차원 파라미터 → 2D/3D)** — 시작점을 사용자 요청대로 압축해 "정말 발산/수렴하는지" 직접 확인:
![pca2d](mujoco/assets/pca_convergence_2d.png)
![pca3d](mujoco/assets/pca_convergence_3d.png)

개별 궤적(원=시작→별=수렴)은 짧고 급격하다(≈10 iter 안에 점프) — **지역적으로는 빠르게 수렴**한다. 하지만 수렴점(별)들이 PC1-PC2 평면 전체에 넓게 흩어져 있다 — **전역적으로는 발산**(서로 다른 곳에 정착). 정량화: 시작점 구름 대비 수렴점 구름의 퍼짐 비율(contraction ratio) = **0.57**(1.0=전혀 안 좁혀짐, 0=한 점 수렴) — feasible 영역 쪽으로 어느 정도 깔때기 효과는 있지만, 그 안에서도 다중 국소해가 뚜렷이 남는다. 색(점수)이 오른쪽 위(고득점, 진한 빨강)와 가운데 왼쪽(저득점, 남색/보라)으로 약하게 분리되는 것도 보여 완전 무작위는 아니고 약한 지형 구조는 있다.

**리스크 재평가**: 지금까지 "공식" 최종값(마진 3.7%, §8b)은 26만개 Sobol **스크리닝으로 미리 걸러진 상위 후보**에서 로컬서치를 시작했기 때문에, 이번 진단(무작위 균등 시작점, 최고 3.38%)보다 훨씬 유리한 조건이었다 — 그래서 3.7%는 신뢰할 만하다(0.47%처럼 나쁜 국소해에 안 걸림, 무작위 시작 중 최선인 3.38%보다도 오히려 낫다). 다만 **좌표하강 자체의 강건성 한계는 실증됐다** — 스크리닝 없이 소수 시드로만 최적화하면 진짜 나쁜 로컬옵티멈(0.47~1%대)에 빠질 수 있다는 게 확인된 것. 실무 함의: **항상 대규모 Sobol 스크리닝(수만~수십만) + 상위 후보 로컬리파인 조합을 유지**할 것, 소수 랜덤시드 단독 로컬서치는 비권장.

**교훈(방법론)**: iteration cap을 늘려서 "정말 수렴하는지" 보자는 접근 자체는 맞았지만, 늘린 뒤 관찰해야 할 지표는 "최종 iteration 도달 여부"가 아니라 **"마지막 N iteration 동안의 점수 변화량"**이었다 — 전자만 보면 "200/200 다 씀=아직 개선중"으로 오판하기 쉽고(이번에 실제로 그렇게 오판할 뻔했다), 후자를 봐야 진짜 정체 여부가 드러난다. 스크립트: `mujoco-sim/mjlab/analysis/ankle_opt_deep_multistart.py`.

### §8e ★알고리즘 교체 — DE(Differential Evolution)로 global 재탐색 (2026-08-12)

사용자 지시: 박스를 넓혀 전역해를 찾고, 알고리즘을 가다듬을 것("adam 같은 걸 써야하나?").

**Adam 기각 이유**: 목적함수가 P99 percentile·max/min·IK 분기선택(atan2 branch)·ROM 폐합 0/1 게이트로 구성돼 대부분 구간에서 미분이 정의 안 되거나 불연속이고, feasible 영역이 박스의 0.01~0.02%뿐인 얇고 끊어진 섬이라 그래디언트 방법이 출발점 대부분에서 무의미하다. §8d에서 실증한 multimodal 특성도 단일점 로컬법(Adam 포함)에는 불리하다.

**채택**: **DE/rand/1/bin** — 이 프로젝트 기존 doctrine([[60_fourbar_optimizer_research]], Deb 3-규칙)이 이미 이 문제군의 표준으로 지정한 방법. **커버리지가 중립(pitch 0°) 근처에서 최대이고, 배굴(+30°, 고부하방향)로 갈수록 오히려 줄어든다** — §7f 이래 "크랭크 오프셋=수요밀집구간 정렬"이라 서술해온 것은 **이 최종 기하(v3c 계열)엔 적용되지 않는다.** 정정.

**원인**: 이 설계의 binding 제약은 토크가 아니라 **발측 요동각(margin 3.7%)**이다. 토크 마진은 어느 pitch에서든 27%+ 남아 목적함수(min-margin, 최악값 하나만 봄) 관점에서 크랭크를 토크방향으로 정렬해도 점수 이득이 없다 — 최적화가 그 자유도를 전부 요동각 확보에 썼다. Agibot/G1의 큰 배굴방향 오프셋(~20°)은 그쪽 설계의 binding 제약이 다르다는(아마 요동각이 덜 타이트한) 방증일 가능성이 높다 — 우리와 동일 목적함수·제약조건으로 최적화한 게 아니라 직접 비교는 조심스럽다.

**미해결 질문**: 토크-정렬을 명시적으로 2차 목적에 넣어야 하는지(margin이 이미 27%+로 넉넉하니 현재로선 불필요해 보이지만, Agibot 같은 실물 레퍼런스가 일관되게 이 방향을 택한다는 건 우리가 놓친 다른 이유—피로수명·모터 발열·기어비 등—가 있을 수 있다는 신호), 후속 검토 필요.

### §8k swing_foot을 목적함수에서 뺀 실험 — 가설 확인됨 (2026-08-12)

§8j에서 제기된 질문("swing_foot이 그 자유도를 뺏고 있는 거 아닌가")을 직접 실험. `swing_foot`을 P99K(최소마진 점수)에서 제외하되 hard 제약(20° 초과 불가)으로는 유지(별도 HARDK 리스트)하고 재최적화.

**결과**: 마진 3.72%→**32.98%**로 급등(당연히 — 진짜 병목을 빼면 다음으로 타이트한 항목인 모터토크 27%대가 새 병목이 됨). swing_foot은 hard 제약 경계까지 밀림(마진 0.15%, 사실상 제한선). 이 조건에서 커버리지 곡선(모터peak×2 환산, pitch 스윕)을 다시 뽑아보면:

| 조건 | 커버리지 정점 위치 | n0A/n0B |
|---|---|---|
| 원래(v3c, swing_foot 포함) | pitch **0~5°** | 14.4°/8.5° |
| swing_foot 제외 | pitch **20~25°**(수요 중앙값 23°에 근접) | 6.7°/1.8° |

**★가설 확인됨**: swing_foot 목적을 빼주면 커버리지 정점이 실제 수요 밀집구간(중앙값 23°) 쪽으로 이동한다 — §8j에서 사용자가 제기한 "발측 요동각이 토크정렬 자유도를 뺏고 있다"는 가설이 맞았다. 단, **크랭크 절대 오프셋(n0A) 자체는 오히려 작아졌다**(14.4°→6.7°) — "정렬"은 n0A 하나의 크기가 아니라 RP_B·RP_r·A_h·B2RP 전체가 같이 바뀌며 만드는 커버리지 곡선의 형태(모양·정점위치)로 나타난다는 뜻. n0A를 정렬의 직접적 대리지표로 쓰면 오독하기 쉽다.

**실무 함의**: 이 프로젝트의 요동각 한계(20°)나 박스 제약이 Agibot류 실물 설계보다 더 타이트해서 토크정렬에 쓸 여유가 없는 것으로 보인다 — 만약 요동각 여유를 늘릴 수 있다면(더 큰 볼조인트, 다른 배치) 토크정렬도 함께 개선될 잠재력이 있다는 뜻.

## §9 ★★★ 감사보고서 — pitch 부호 불일치 전수조사 (2026-08-12)

사용자 지시: "어디까지 영향받는지 처음부터 검토하라. 설계 최적화 과정을 단계별로 나열하고, docs에 정리하면서 무엇이 문제가되는지 스스로 의심하고, 감사하라." 아래는 그 조사 과정을 **가감 없이**(중간에 낸 오판 포함) 기록한다.

### §9a 발단

사용자가 렌더 이미지(§8j 3D 비교)를 보고 "발끝이 위로 갈수록 크랭크가 왜 더 접히냐"고 지적 → pitch 스윕 렌더를 만들어 직접 봤더니 **발끝 마커가 pitch 증가(−50→+30)에 따라 내려간다** — docs/51에서 FK로 검증했던 "+pitch=배굴(발끝 위)"와 반대로 보임.

### §9b 1차 조사 — "부호반전" 가설 (틀린 세부 아님, 방법이 성급했음)

로봇 실제 회전행렬(qpos=+20°)과 2-RSU `footR(tp=+20°,tr=0)`를 **월드/바디 프레임 그대로** 직접 대조:
- 로봇 pitch: `[[1,0,0],[0,0.94,0.342],[0,-0.342,0.94]]` — 로컬 X 고정, Y-Z 평면 회전
- 2-RSU tp: `[[0.94,0,0.342],[0,1,0],[-0.342,0,0.94]]` — 로컬 Y 고정, X-Z 평면 회전

**두 행렬이 도는 평면(축) 자체가 다르다**고 보고 "축이 통째로 swap됐다"고 사용자에게 보고함(§8 상단 배너에 그렇게 적었었음).

### §9c ★셀프 감사로 발견한 1차 조사의 결함

이 비교는 **로봇의 `ankle_pitch_link` 로컬 프레임**과 **2-RSU 툴이 독자 선언한 로컬 프레임("UJ 원점·X전방·Y좌·Z상")**을 서로 다른 두 좌표계인데 **같은 좌표계인 것처럼 직접 대조**한 것 — 방법론적으로 무효할 수 있음을 뒤늦게 자각. 두 로컬 프레임의 실제 정렬관계를 검증 안 하고 raw 행렬을 비교하면, 단순히 "같은 회전을 서로 다른 이름의 축으로 부르는" 상황도 "축이 다르다"고 오판할 수 있다.

**검증**: 로봇의 `ankle_pitch_link` 자체의 월드 자세(서있는 keyframe)를 확인:
```
local X axis -> world (0,1,0)   # world Y
local Y axis -> world (-1,0,0)  # world -X
local Z axis -> world (0,0,1)   # world Z(up) — 일치
```
그리고 발끝(toe_link) 위치를 이 로컬 프레임으로 변환: `(-0.022, -0.188, -0.050)` — **로컬 −Y 방향이 압도적**(발끝은 로컬 Y축, X축이 아님).

→ 로봇의 `ankle_pitch_link` 로컬프레임은 **X=외측(lateral), Y=전방(toe), Z=상(up)**. 2-RSU 툴이 자칭한 프레임(X=전방)과는 **X·Y 라벨이 정반대로 붙어있을 뿐**, pitch가 회전시키는 물리적 평면(외측축 기준 전후-상하 평면)은 **동일한 회전 자유도**를 가리킨다. §9b에서 "축이 다르다"고 한 건 **좌표축 이름표가 다르게 붙은 두 프레임을 혼동한 것**이었다 — 정정.

### §9d 프레임에 무관한(라벨 독립) 최종 재검증

각 시스템이 **자기 자신의 선언**만으로 "+방향이 배굴인지 저측굴곡인지" 판정(교차 프레임 비교 없이):

- **로봇**: 실제 toe_link 메쉬, 실제 keyframe, 실제 qpos — FK로 직접 측정(§8i 이전에 이미 완료): `+qpos → 발끝 world Z 상승` = **배굴**. (프레임 라벨과 무관한 100% 직접측정, 가장 신뢰도 높음)
- **2-RSU 툴**: 툴 스스로 선언한 "X전방·Z상"을 그대로 신뢰해서 +X점(자칭 발끝)의 world_z를 tp의 함수로 계산 → `world_z = −sin(tp)`, **tp 증가 시 감소** = 툴 자신의 선언 기준으로 **저측굴곡**.

**결론(재확정)**: **2-RSU 툴의 "+tp" = 로봇의 "−qpos"(저측굴곡 방향)** — 순수 부호반전(§9b에서 의심했던 "축 자체가 바뀜"은 좌표축 명명 차이에서 온 착시였고, 실제로는 **§9b의 원래 가설(부호반전)이 맞았다**, 다만 그걸 확인한 방법(프레임 안 맞춘 raw 행렬 비교)이 부적절했을 뿐).

**roll은 아직 이 수준으로 재검증 못 함 — 미결.** (symmetric ±20°라 pitch보다 영향은 작지만, (pitch,roll) 동시쌍의 상관구조가 깨질 수 있어 완전히 무해하다고 단정 못 함.)

### §9i pitch 수정 적용 + 재최적화 착수 (2026-08-12 저녁, 진행중)

사용자 지시: roll 재검증과 **동시에**, 영향받지 않는 부분(raw 수요 데이터 자체)을 활용해 즉시 재최적화 진행.

**적용한 수정**(`ankle_opt_de.py`):
- `THP = radians(-A[:,0])`(★negate, 기존은 `radians(A[:,0])`) · `G1P`도 동일 negate.
- ROM exclude 필터(`A_full[:,0]>=PLO & <=PHI`)는 **로봇 raw qp_deg 기준 그대로 유지**(이건 안 바뀜 — §9e에서 이미 "필터링 자체는 영향 없음" 확인됨).
- `make_ws()`의 H1 폐합그리드: `linspace(PLO,PHI,19)` → **`linspace(-PHI,-PLO,19)`**(qp∈[-50,30] → 기구모델 tp=-qp∈[-30,50]로 매핑되므로).
- roll(tr)은 **미변경**(§9d 미결이라 보수적으로 유지, 대칭이라 리스크 낮음).

## §10 ★★★ 좌표계 처음부터 재구축(패치가 아니라 재유도) + 2번째 버그 발견 (2026-08-13)

사용자 지시(2026-08-13): "①시뮬레이션 회전관절 방향/좌표계와 우리 kinematics를 다시검토해서 동일하게 맞춰라(패치가 아니라 정합), ②실제 데이터로 AB(모터)-RP(관절) 대응을 검증해라, ③RP·시뮬레이터 부호가 안 맞아서 커버 안 되는 거 아닌지, ROM(Roll±20·Pitch 배굴30/저측굴50)이 맞게 걸려있는지, 실측에서 배굴방향 토크가 많다는 점 고려해서 재검토해라."

§9의 수정(`tp = -qp_deg` negate)은 **증상 패치**였다 — 어떤 좌표계가 옳은지 처음부터 유도하지 않고, "방향이 반대인 것 같으니 부호만 뒤집자"는 식이었다. 이번엔 로봇의 실제 MJCF 관절체인에서 회전행렬을 직접 유도하고, MuJoCo FK로 **동시(pitch+roll) 자세**에 대해 검증한 뒤, 2-RSU 전체 기구학(anchors/axle/rod IK/moment arm/swing 각)을 그 위에 처음부터 다시 세웠다.

### §10a 회전행렬 유도 + FK 동시검증

로봇 MJCF: `L_ankle_pitch_joint axis="-1 0 0"`(정강이 로컬 프레임 기준) → `L_ankle_roll_joint axis="0 1 0"`(그 pitch-회전된 프레임, 즉 `ankle_pitch_link` 자신의 프레임 기준 — 관절체인상 pitch 다음에 적용). 따라서 합성 회전은:

$$R(t_p,t_r) = R_{pitch}(t_p)\,R_{roll}(t_r), \quad R_{pitch}(q)=\begin{bmatrix}1&0&0\\0&\cos q&\sin q\\0&-\sin q&\cos q\end{bmatrix},\quad R_{roll}(q)=\begin{bmatrix}\cos q&0&\sin q\\0&1&0\\-\sin q&0&\cos q\end{bmatrix}$$

**검증**: `R_pitch(15°)·R_roll(10°)`을 MuJoCo에서 `L_ankle_pitch_link`→`L_foot_link` 실제 상대회전(pitch=15°·roll=10° **동시** 부여, FK)과 비교 — **완전 일치**(atol 1e-3). §9는 pitch 단독·roll 단독만 각각 확인했었는데, 이번엔 **동시 자세**로 재검증해 커플링 자체도 맞다는 것까지 확인했다.

로컬 프레임 축(⁠`ankle_pitch_link` 바디 프레임, FK로 직접 측정): **X=외측(pitch 회전축 자신, 순수 pitch로는 안 움직임)·Y=전후(roll 회전축, 실측 L_toe_link가 로컬 Y≈−0.188m → 음(−)Y=발끝/전방, 양(+)Y=뒤꿈치/후방)·Z=상(중립자세에서 로컬 Z축 이미지 → world (0,0,1) 확인됨)**.

### §10b 2-RSU 기구학 처음부터 재유도

**앵커(발에 고정, R(tp,tr) 적용됨)**: `(side·RP_r, +RP_B, −RP_h)` — RP_r→X(외측), RP_B→+Y(후방/뒤꿈치, "RP_B↑→뒤꿈치돌출↑" 문서기술과 일치), RP_h→−Z(피벗 아래, `/ankle.html` 자기선언 `앵커=(−RP_B,±RP_r,−RP_h)`의 Z부호는 그대로 — Z축 자체는 애초에 의심대상이 아니었음, X/Y만 뒤바뀌어 있었다).

**액슬(정강이에 고정, 회전 안 받음)**: `(side·A_h, 0, B2RP+(A2B if up))` — Z가 **양수**(피벗보다 위, 실제로 액추에이터가 정강이 위쪽에 있는 것과 일치, `ankle.html`의 `crankC()` Z=+B2RP와도 일치, 이 축도 애초에 의심대상 아니었음).

**tp=qp_deg, tr=qr_deg를 그대로(부호변환 없이) 먹인다** — R(tp,tr) 자체가 이미 로봇 실제 관절체인과 검증된 형태이므로, §9처럼 별도 negate 패치가 전혀 필요없다. 크랭크 회전축은 로컬 X(액슬의 lateral 축, 모터축 방향과 일치)이므로 크랭크 핀은 로컬 Y-Z(전후·상하) 평면에서 스윙 — 이 부분이 이전 프레임(X-Z 평면 스윙 가정)과 달라진 지점. 로드 IK는 동일한 원-교차 공식을 (Y,Z)쌍·X를 고정오프셋으로 재유도(§10 코드 참조, `mujoco-sim/mjlab/analysis/ankle_opt_de_v2.py`).

**중립자세 IK 폐합·ROM 전역(−50~+30°) 단조성 스모크테스트**: v5c류 파라미터로 pitch −50→+30° 스윕 시 크랭크각이 매끄럽게 단조증가(1.05°→58.37°), ROM 전 구간 폐합 성공 — 사용자 요청 ②(AB-RP 실데이터 대응)의 1차 확인.

### §10c ★두 번째 독립 버그 발견 — swing_foot 공식이 여각(90°−진짜각)을 계산하고 있었다

새 기하로 첫 재최적화(v6a/b/c)를 돌리자 **셋 다 동일하게 score −3.35% 근방 정체**(이전 §9j의 +3.8%에서 크게 후퇴) — swing_foot 마진만 확인하니 **−335%**(요구각 87°, 한도 20°)라는 터무니없는 수치. 중립자세에서 직접 로드방향 벡터·기준축 내적을 손으로 재계산하니:

- 진짜 콘각(arccos, 로드가 기준축에서 얼마나 기울었는지) = **26.36°**
- 코드가 실제로 계산한 값(arcsin) = **63.64°** = 90° − 26.36° (여각!)

원인: swing_foot 공식을 크랭크측(swC) 공식을 그대로 베껴 썼기 때문. **swC(크랭크측)는 "회전평면에서 얼마나 벗어났는가"** 개념이라 arcsin이 맞다(로드가 평면 안에 있으면 0°, 축과 나란하면 90°). 반면 **swF(발측)는 진짜 원뿔각(boresight cone) 제약을 갖는 로드엔드 볼조인트**라 "기준축에서 얼마나 벗어났는가" 개념 — 이건 arccos다. 두 관절의 물리적 제약 종류가 다른데 같은 공식을 썼던 게 버그. `rodgeo()`에서 `swF = degrees(arccos(...))`로 수정(기존 arcsin) — 수정 즉시 동일 지점에서 마진이 −335%→−242%로 완화(여전히 위반이지만 방향이 맞게 줄어듦), 재최적화(v7a/b/c) 착수.

이 버그는 **§9의 pitch 부호버그와는 완전히 독립적인 별개의 결함**이며, §8~§9j까지의 모든 swing_foot 수치(포함 "3.8% binding" 결론)에도 함께 영향을 준다 — swing_foot이 그동안 계속 병목(binding)으로 보고돼 왔는데, 그 병목 자체의 크기가 잘못 계산돼 있었다는 뜻. 박스 코너 그리드서치로 중립자세 swing_foot 최소값이 박스 안에서 13.6°(한도 20° 이내)까지 나오는 것을 확인해 **박스 자체가 구조적으로 불가능한 건 아님**을 확인 후 v7 재실행.

### §10d 실측 데이터 — 배굴(pitch+) 방향 밀도·토크 재확인

사용자 지적("실측에서 발끝 위로 가는 방향 토크 많이 걸리던데") 정량 재확인: ROM 필터 후 표본의 **72%가 pitch>15°, 97%가 pitch>0°, 중앙값 19.1°** — 즉 실사용 시간 대부분이 배굴(발끝 위) 쪽에 쏠려 있다. 반면 pitch 구간별 |τp| RMS/P99 자체는 구간별로 크게 차이나지 않음(RMS 12~21, P99 35~62 전 구간 고르게 분포) — **피크가 배굴에서 특별히 큰 게 아니라, 배굴 자세에 머무는 시간(=RMS/P99 계산에 들어가는 표본 수)이 압도적으로 많다.** 이건 현재 목적함수(전체 실측 표본의 percentile)가 이미 자동으로 반영하는 종류의 편중이라, 별도 가중치 없이도 올바르게 잡힌다 — 문제는 편중을 못 잡는 게 아니라 **기구가 그 밀집구간에서 유리한 전달비를 못 낸다**는 쪽(§10e).

### §10e 모멘트팔(전달비) vs pitch — 새 기구학으로도 여전히 배굴에서 불리

v5c급 파라미터로 새 기구학의 모멘트팔(토크capability 결정요인)을 pitch 전역에 대해 직접 계산: **armA는 pitch≈−20°(중립보다 살짝 저측굴 쪽)에서 최대(65.0), armB는 pitch≈+5°에서 최대(55.1)** — 결합 커버리지는 **pitch≈−20~0°에서 최대, +30°(배굴/고밀도 구간)로 갈수록 단조감소**(예: A_r/B_r 65/55 기하에서 62.25→51.53). **§9j에서 부호패치 후 봤던 것과 같은 방향의 결론**(중립·저측굴 쪽 유리, 배굴 쪽 불리)이 **처음부터 다시 유도한 올바른 기구학에서도 재현됨** — 즉 이건 부호버그의 부산물이 아니라, 이 2-RSU 배치(액슬 위·앵커 아래, RP_B/RP_r 박스 범위)의 **구조적 특성**이다.

**결론**: pitch 합성부호(§9) + swing_foot 공식(§10c) 두 버그를 **모두** 고친 뒤의 참값은, 확정 박스(A_r/B_r 40~65·RP_B 50~75·RP_r 35~50·A_h 35~45·B2RP 170~200·RP_h −10~10)로는 **ROM 전역(pitch −50~+30°·roll ±20°)에서 swing_foot≤20°를 만족할 수 없다** — 필요각이 최대 ~54°(한도의 2.7배)까지 간다. §9j까지의 "swing_foot 3.8% 여유로 겨우 feasible" 결론은 **두 버그가 겹쳐서 우연히 그럴듯한 숫자를 낸 것**이었다(부호버그가 ROM을 엉뚱한 쪽으로 매핑 + 공식버그가 필요각을 원래보다 작게(여각으로) 계산 — 두 오차가 우연히 어느정도 상쇄됐을 가능성이 있다. 정확한 상쇄 비율은 추가분석 없이는 단정 못 함).

**사용자 확인 필요(박스 무단 확장 금지 원칙 유지, §6/§8e 반복지적 학습)**:
1. RP_B/RP_r 하한을 더 낮출 수 있는지(패키징상 40mm 미만 발볼 폭 여유가 있는지),
2. B2RP 상한(200mm)을 더 늘릴 수 있는지(정강이 스택 길이 여유),
3. 아니면 **볼조인트 요동각 한도(SWL_F=20°) 자체를 완화**할 수 있는지(§7j에서 검토했던 광각 스페리컬 부품 재고려),
4. 혹은 2-RSU 배치 자체(액슬-앵커 상대위치, 예: A_h를 RP_r과 다르게 벌리는 등)를 재설계할지.

이 중 하나는 반드시 필요 — 지금 확정된 박스+요동각 조합으로는 물리적으로 안 닫힌다.

### §10g ★실측 replay 기준으로는 더 심각 — 전형적 자세 99%가 위반

위 §10f는 ROM 전역 그리드(17×13 격자, 물리적으로 가능한 전체 자세공간)에 대한 최악값이었다. **실제로 로봇이 다니는 자세(실측 θp(t),θr(t) 13,503샘플)만으로 다시 계산**하면:

- swing_foot 요구각: **중앙값 39.7°, P99 48.2°, 최댓값 52.9°** (한도 20°)
- **실측 표본의 99.1%가 20° 한도를 초과**

즉 이건 ROM 구석의 희귀 코너 케이스가 아니라 **평소 걸음 자세 거의 전부**에서 발생하는 위반이다. §7~§9j에서 계속 "swing_foot이 아슬아슬하게 binding(3.8% 여유)"이라고 보고해온 것은, pitch 부호버그(§9)와 swing_foot 여각버그(§10c)가 함께 작용해 우연히 그럴듯한 숫자를 만든 것이었고, **실제로는 이 지표가 현재 박스에서 전혀 성립하지 않는다.**

사용자 질문 ③("실험 데이터의 RP와 시뮬레이터 부호가 안 맞아서 커버 안 되는 거 아닌가")에 대한 답: **맞다 — 정확히 그것 때문이었다.** 부호(§9)와 여각(§10c) 두 버그가 겹쳐서 "커버된다"는 착시를 만들었고, 둘 다 고친 지금은 "커버 안 된다"가 진짜 결론이다. ROM 방향 자체(Roll±20·Pitch 배굴30/저측굴50)는 §9d~§10a에서 로봇 MJCF·FK로 재검증되어 맞게 걸려 있다 — 문제는 ROM의 방향이 아니라, **그 ROM 전역에서 이 2-RSU 배치가 요구하는 발측 볼조인트 요동각이 애초에 20° 한도 안에 못 들어간다는 기구학적 사실**이었다.

다음 단계는 §10f 끝의 4가지 옵션(박스 하한 완화·B2RP 상한 완화·SWL_F 완화·배치 재설계) 중 사용자 결정을 기다린다.

### §11a 스윕 인프라 (`ankle_opt_de_v3.py` + `run_sweep.py`)

`ankle_opt_de_v2.py`(§10) 기반에 4개 MODE 추가: `base`(확정 박스 그대로) · `coupled`(A_h=RP_r 강제, decode 후 override) · `widebox`(BOX A_h=RP_r=(40,45)) · `noswingfoot`(swing_foot을 P99K에서 제외, §8k와 동일 개념이나 SS10 정정기하 기준으로 재실행). 세대별 **margin 항목 전체**를 JSONL로 로깅(`gens_<mode>_<tag>.jsonl`)해 term-vs-iteration 추적이 가능하게 함. `run_sweep.py`가 시드별 서브프로세스를 bounded parallelism으로 오케스트레이션.

**인프라 버그 3종 발견·수정(기록)**:
1. **BLAS 스레드 과다구독**: numpy가 프로세스당 전체 코어 수만큼 스레드를 쓰는 게 기본값이라, 8개 워커가 각자 8스레드씩 써서 load average 80+까지 치솟음(8코어 머신). `OMP_NUM_THREADS=1` 등 4개 env var로 강제 단일스레드화해 해결.
2. **CSV 재파싱 메모리 폭탄**: 워커마다 265MB/20만행 rosbag CSV를 `csv.DictReader`로 새로 파싱 → 프로세스당 RSS 1.8GB, 8개 동시실행 시 스왑까지 가득 참(15GB RAM 초과). G1 배열을 한 번만 전처리해 `.npz` 캐시(2.2MB)로 저장하고 워커는 그걸 로드하도록 수정 → 프로세스당 RSS 115MB로 16배 감소.
3. **평가함수 서브샘플링 편향**: eval() 1회가 13,503(수요)+45,167(G1) 전샘플을 재생해 세대당 ~7s — 100시드×4모드가 비현실적으로 느려서 서브샘플링 도입. 첫 시도(균일랜덤)는 `torque_pk`처럼 `.max()` 기반인 지표에서 진짜 최댓값 표본이 빠질 위험이 있어 실제로 +19.7pp 오차 발생. 수정: **percentile용 풀(비편향 균일랜덤)과 peak용 풀(원자료 각 컬럼 상위15% 합집합, 진짜 최댓값 보존)을 분리** — peak 지표는 전샘플 대비 0.000pp 정확히 일치, percentile 지표(torque/tn/rod)는 ±0.1~1.9pp 오차로 검증됨(2개 대표점 스팟체크). ~4배 속도향상.

## §12 ★마운트 자유도(프리틸트) — swing_foot 지표 정정 + 저측굴곡 ROM 실사용 (2026-08-13)

### §12a 사용자 지적: "중립(RP 0°)에서 요동각 0°여야"

맞는 지적. v3의 `swF = arccos(|u·footN|)`은 **발바닥 법선을 마운트축으로 고정** 가정 — 실제로는 볼스터드 장착 방향이 자유 설계변수다. 옳은 제약: 발 프레임에서 ROM 전체에 걸친 로드 방향 다발(부채)을 담는 **최소 외접원뿔 반각** ≤ 요동한도. 마운트 방향 = 원뿔 중심축 선택일 뿐이라 DE 변수 추가 없이 지표만 바꾸면 된다. `A_h=RP_r` 구속은 중립의 횡성분 정렬만 만드는 부분해(§11 Q2에서 성능중립 확인)로 불필요.

base 100시드 최적점(s5000)에서 정정 계산: 로드A 필요원뿔 **41.6°**(마운트 발법선에서 9.2° 틸트), 로드B **43.4°**(14.7°) — 구지표 50.6/53.7° 대비 ~9–10° 회수. 그러나 한도 20°의 2배대로 결론(불가) 유지. 중립자세 방향은 원뿔 중심에서 13–20° 벗어남(pitch ROM 비대칭 −50~+30 탓) — "중립에서 0°" 장착이 오히려 준최적.

### §12b 저측굴곡(발끝 내림) 실사용 — 정책·G1 실기 모두 거의 안 씀

| 데이터 | pitch<0° | <−10° | <−20° | 최심 |
|---|---|---|---|---|
| 정책 flat | 1.28% | 0.46% | 0.077% | −31.4° |
| 정책 rough | 3.15% | 0.39% | 0.011% | −26.1° |
| G1 실기 | (규약 상이) 한쪽 밴드 폭 ~27° | — | 0.87% | −26.6° |

저측굴곡 중 |τp| 중앙 5–15 N·m(낮음). **HW 캡 −50°는 학습데이터 근거 없음** — −35°로 줄여도 관측범위(−31°) 커버.

### §12c 저측굴곡 캡 축소 → 필요원뿔 (마운트 최적, 배굴 +30·roll ±20 고정, s5000 기하)

−50°→43.4° / −35°→34.7° / −25°→30.5° / −15°→26.6° / −10°→24.8° — **전부 ✗(>20°)**. 배굴 +30 + roll ±20만으로 이미 ~25° 필요(부채 반폭 ≈ pitch 스팬/2 × (1−RP_B/L) + roll 기여, RP_B≪L이라 기하로 상쇄 불가). **결론: 마운트 프리틸트 + ROM 트림을 다 합쳐도 20° 미달 — 발측 S조인트 유지로는 불가. 발측 U조인트(원뿔한계 소멸) 또는 요동 35°+ 광각 스터드 필요**(딥리서치 Q4 진행중). 요동한도는 사용자 확정 **20°**(JS6 13° 탈락).

## §13 ★★★ 최종 판정 — 수직 20° 제약 확정 + 크랭크 분기(φ0) 숨은제약 발견 + 발측 S조인트 불가 (2026-08-13)

### §13a 사용자 확정 제약
광각 볼스터드 불가 · 요동각 **20° 고정** · **수직 설치만**(스터드⊥발바닥). → §12의 마운트 프리틸트 자유도 소멸, v3의 `swF=arccos(|u·footN|)`(발법선 고정축)이 그대로 옳은 지표로 복귀.

### §13b 크랭크 분기 숨은제약 발견 (φ0=180 하드코딩)
v1~v3의 IK 분기 선택(`pick = |wrap(s−π)|` 최소)과 중립크랭크 윈도우(180°±75°)가 **크랭크가 앵커 반대쪽(φ≈180°)을 향하는 패밀리만** 탐색하도록 고정하고 있었다. 크랭크를 앵커 쪽(φ≈0°)으로 향하면 핀 y=+r이 앵커 y=RP_B에 근접해 **로드가 수직에 가깝게 매달리는데, 모멘트팔(|Ty|=r)·전달비는 동일**하다. 동일 기하 손계산: 중립 요동 23~40°→9~11°, [−10,+30]×±15 박스 최대 요동 58.5→35.1°. 워크플로 적대검증(§13e)도 독립적으로 "±75° 윈도우는 근거 없는 재도입 숨은규칙"으로 지적(감사 계보: A_h=RP_r 해제→로드길이 자유화→ax트림→**φ분기**). 구현: `ankle_opt_de_v5_romscan.py`(argv[7]=φ0).

### §13c 3중 증거 — 발측 S조인트(수직 20°)는 어떤 ROM 박스로도 불가
1. **해석적 하한 스캔**(신규, `swing_floor_scan.json`): 기하를 요동각 최소화에만 바치고(토크 무시, 전달비≥0.3만 유지, φ0=0 패밀리) 36개 ROM 박스 전수 DE — **전부 >20°**. 최소는 [−10,+25]×±10의 22.6°(이 박스는 배굴 사용 중앙값 +19·P99 +42를 거의 커버 못함). 하한은 배굴캡·roll에 지배(배굴 +5°당 약 +4°, roll ±5°당 약 +3°), 저측굴곡 트림은 거의 무효.
2. **DE 교차검증**: v5 [−10,+30]×±15 → 필요 28.8°(해석 하한 28.8°와 일치, 토크마진 +19% = 요동각 단독 병목). 구패밀리 v4 동일 박스는 50.7° — φ0=0으로 21.9° 개선해도 20° 미달.
3. **워크플로 검증단 예측**(§12c 데이터 기반): "사용을 커버하는 어떤 박스도 수직 20° 불가, U조인트가 증거상 1순위" — 계산으로 확정됨.

### §13d 판정
> **발측 볼조인트(요동 20°·수직 설치)로는 2-RSU 발목이 성립하지 않는다(ROM 축소·기하 최적화·크랭크 재배치 전부 소진). 설계 방향 = 발측 U조인트(십자핀) 전환 — 원뿔한계 개념 소멸, 로드 스핀은 크랭크측 S가 흡수(정통 RSU 위상). 이 구성의 기대 성능은 이미 측정되어 있음: noswingfoot 100시드 스윕 = 전 항목 feasible, 최소마진 +36.6%.** 상세 명세·감사 36건·프로세스 게이트는 [[72_ankle_2rsu_objective_spec_and_direction]].

### §13e 목적함수 감사(워크플로, 6에이전트 3렌즈)

## §14 ★★★ 사용자 하드 결정(JS6 ±20°·수직) + 수요풀 v4 확장 + ROM 공동설계 프런티어 (2026-08-13)

### §14a 결정 (사용자, 최종)
