## 0. 크리티컬 — 속도를 막는 장치가 없습니다 ★실기 안전 직결★

### 쉬운 말로

모터가 얼마나 **빨리** 돌지를 제한하는 장치가 어디에도 없습니다. 빨리 돌던 모터를 급히 세우면
발전기처럼 전기가 전원으로 되돌아가고, 전압이 올라가면 **같은 전원을 쓰는 모터가 전부 동시에**
스스로 힘을 끊습니다. 서 있는 로봇이라면 그대로 주저앉습니다.

### 실측 (벤치, 2026-09-05)

축에 아무것도 안 달린 가벼운 로터인데도:

```
0.03초   534도/초
0.15초  1072도/초   ← 초당 3바퀴
0.73초    76도/초
0.85초     0도/초   ← 전압 보호로 두 모터 동시 정지
```

0.85초 동안 1.27바퀴를 돌았습니다. 고장값을 읽어 보니 **비트 3 = 과전압**이었습니다.

### 왜 기존 장치로 안 막히나

`safety.max_delta_deg`(50도)는 **위치 오차**를 묶는 것이지 **속도**를 묶지 않습니다. 오늘 오차는
50도로 잘 묶여 있었는데 속도는 초당 1072도까지 올라갔습니다. 저희도 이 설정을 속도 안전장치로
오해했었고, 실측으로 아니라는 걸 확인했습니다.

### 쓰이지 않는 안전선 두 개

1. **명령의 속도 자리가 비어 있습니다.** `MitCommand` 는 다섯 값을 가지는데
   (`tau = kp*(위치오차) + kd*(속도오차) + 토크`), `Leg.build_commands`(`robots/leg.py:490`)는
   위치와 게인만 채웁니다.
2. **모터 자체의 속도·전류 상한을 설정하지 않습니다.** 제조사 파라미터 표에 있습니다:

   ```
   VELOCITY_LIMIT = (0x7017, float32, "limit_spd")
   CURRENT_LIMIT  = (0x7018, float32, "limit_cur")
   ```
   (출처: 벤더 공식 SDK `robstride_dynamics/protocol.py`)

   `src/huphy/` 전체에서 `limit_spd`/`limit_cur`/`0x7017`/`0x7018` 검색 결과 **0건**입니다.
   펌웨어가 스스로 지킬 수 있는 안전선이 **비어 있는 채로** 돌고 있습니다.

### 실기에서 더 나쁠 수 있는 이유

벤치는 무부하 로터였습니다. 실기는 다리 무게가 실려 **움직이는 에너지가 훨씬 큽니다.** 같은 급정지에
되돌아오는 전기도 그만큼 크고, 전압 보호는 **한 모터가 아니라 같은 전원의 전부**를 멈춥니다.

### 막을 방법 (강한 것부터)

1. **모터에 속도·전류 상한을 심는다** — 펌웨어가 지키므로 상위 코드가 실수해도 안전합니다.
   커미셔닝 때 한 번 써 두면 됩니다.
2. **명령의 속도 자리를 쓴다** — 목표 속도를 함께 보내면 모터가 그 속도로 접근합니다.
3. **목표를 계단이 아니라 경사로 준다** — 큰 목표를 시간에 걸쳐 나눠 보냅니다.
4. **제어 중에도 고장을 읽어 즉시 멈춘다** — 지금은 제어 중 고장을 아예 보지 않습니다(2번 항목).

## 0a. 정정 — 속도 제한 장치는 "있습니다". 다만 속도를 제한하지 않습니다

> 0절에서 "속도를 제한하는 것이 아무 데도 없다"고 적었습니다. **틀렸습니다.** 아래가 실측으로
> 확인한 정확한 내용입니다. 0절은 남겨 두되 이 절을 함께 읽어 주십시오.

### 쉬운 말로

`clamp_jump` 이 그 역할을 합니다. 주석에도 "클리핑 = 속도 제한이다"라고 적혀 있습니다. 그런데
이것이 실제로 자르는 것은 **위치 오차**이고, 위치 오차를 자르면 잘리는 것은 **토크**입니다.
속도는 그 결과일 뿐이라 **부하에 따라 달라집니다.**

### 실측 (2026-09-05, 같은 25도 점프, kp=30)

| `max_delta_deg` | 이론상 토크 상한 (kp x 오차) | 실측 최대 토크 | 실측 최고 속도 |
|---|---|---|---|
| 50.0 (기존) | 26.18 N·m | 4.89 N·m | **초당 336도** |
| 3.0 | 1.57 N·m | 1.26 N·m | **초당 49도** |

`50.0` 은 100 Hz 에서 초당 5000도에 해당해 RS04 무부하 최고속도(초당 약 1140도)의 4.4배입니다.
**한 번도 걸리지 않으므로 없는 것과 같습니다.** 반대로 `3.0` 은 이론상 초당 300도여야 하는데 실측은
초당 49도였습니다 — 토크가 1.26 N·m 로 잘려 그만큼밖에 못 가속했기 때문입니다.

즉 이 값은 **토크 상한**으로 이해해야 하고, 같은 값이라도 `kp` 를 바꾸면 뜻이 달라집니다.

### 왜 중요한가

- 이름과 주석이 "속도"라고 말하는데 실제로는 토크를 자릅니다. 걷기 속도를 맞추려고 이 값을 올리면
  **토크 상한이 같이 올라갑니다** — 안전장치인 줄 알고 만진 값이 안전장치를 해제합니다.
- `control_hz` 를 바꾸면 같은 값의 뜻이 조용히 바뀝니다(초당 몇 도인지가 달라짐). 설정에는 그 결합이
  아무 데도 적혀 있지 않습니다.
- **진짜 속도 상한은 여전히 없습니다.** `MitCommand.velocity_deg_s` 는 비어 있고, 모터 자체의
  `limit_spd (0x7017)` 는 한 번도 설정되지 않습니다(0절).

### 수정안

1. 주석을 사실대로 고칩니다 — "위치 오차를 잘라 토크를 제한함. 속도는 부하에 따른 결과임."
2. 설정을 초당 각도로 받고 내부에서 `control_hz` 로 나눕니다. 그러면 제어 주기를 바꿔도 뜻이
   유지됩니다.
3. 진짜 속도 상한이 필요하면 모터의 `limit_spd (0x7017)` 를 커미셔닝 때 한 번 써 두는 것이
   가장 확실합니다 — 통신이 끊겨도 모터 안에 남아 있습니다.

## 0b. 크리티컬 — 온도 자리의 위쪽 4비트를 온도로 계산합니다

### 쉬운 말로

모터가 보내는 온도 칸의 **맨 앞 비트에 온도가 아닌 다른 표시**가 함께 실려 옵니다. 지금 코드는 그걸
온도의 일부로 계산해서, 33도를 **3309.8도**로 읽습니다. 온도가 오락가락하는 것처럼 보였는데,
실제로는 그 비트가 켜졌다 꺼졌다 한 것이었습니다.

### 증상 (실측, 2026-09-05, 같은 모터·같은 순간)

```
수신기 경로   원시값 0x814A = 33098 -> 3309.8도
커미셔닝 경로 원시값 0x014A =   330 ->   33.0도
차이          0x8000  (맨 위 비트 하나)
```

맨 위 비트를 떼면 **정확히 33.0도**로 두 경로가 일치합니다. 다른 관측값도 모두 맞습니다.

| 보고된 값 | 원시값 | 맨 위 비트 제거 후 |
|---|---|---|
| 3309.8 | 0x814A | **33.0도** |
| 3312.8 | 0x8168 | **36.0도** |
| 3308.8 | 0x8140 | **32.0도** |

셋 다 방 온도로 말이 됩니다. 옆 모터(RS03)는 같은 시각 36.0도로 정상이었으므로, 이 비트는 **모터나
상황에 따라 켜집니다.**

### 위치

`src/huphy/motors/robstride/codec/mit.py:124-135`

```python
temp_u = (data[6] << 8) | data[7]
...
float(temp_u) / 10.0
```

16비트를 통째로 온도로 씁니다. 매뉴얼(p.37)은 "Byte6~7 권선 온도(0.1도 단위)"라고만 적고 있어
상위 비트의 뜻은 나와 있지 않습니다.

### 왜 위험한가 (실기)

- **진짜 과열을 놓칩니다.** 130도에서 이 비트가 켜져 오면 13,000도로 표시되고, "말이 안 되는 값"으로
  걸러내면 과열 경보 자체가 사라집니다.
- **반대로 헛경보가 납니다.** 저 값을 그대로 믿으면 33도인 모터가 즉시 과열로 차단됩니다.
- 저희도 이 값 때문에 "온도 인코딩이 모델마다 다른 것 같다"는 **틀린 결론**을 한 번 내렸다가
  뒤집었습니다. 진단을 두 번 헤매게 만든 값입니다.

### 수정안

```python
temp_u = ((data[6] << 8) | data[7]) & 0x7FFF   # 맨 위 비트는 온도가 아님
```

다만 **그 비트가 무엇을 뜻하는지는 확인되지 않았습니다.** 벤더에 문의하거나, 비트가 켜지는 상황을
기록해 두면 좋겠습니다(저희 관측으로는 RS04에서 자주, RS03에서는 안 켜졌습니다). 단순히 버리기보다
**따로 꺼내 기록**하는 편이 나을 수 있습니다.

## 0c. ~~크리티컬~~ **철회** — "전원 켜기 전에 각도를 묻는다"는 지적은 틀렸습니다

> **2026-09-05 실측으로 철회합니다.** 아래 원문은 남겨 두되, 그대로 믿지 마십시오.
>
> 저는 "전원이 꺼진 모터는 명령 프레임에 답하지 않으므로, 전원을 켜기 전에 각도를 물으면 0/6이
> 된다"고 적었습니다. **직접 확인해 보니 꺼진 모터도 명령 프레임에 정상적으로 답합니다.**
>
> ```
> disable_torque() 를 보낸 뒤 0.5초 / 1.0초 / 2.0초 지나서 각각 물어봄
>   -> 무응답 모터: []   (즉 두 모터 다 답함)
> 같은 상태에서 5도 어긋난 목표를 3초간 보냄
>   -> 움직인 양 +0.00도, 토크는 정확히 0    (힘은 확실히 꺼져 있음)
> ```
>
> 즉 **응답 여부로는 전원 상태를 알 수 없습니다.** 0/6이 났던 진짜 원인은 0d절의 2 ms 수신 창
> 하나뿐입니다. 이 절의 "순서" 지적은 근거가 없으니 반영하지 마십시오.
>
> 저희 코드에 넣은 `biped.enable()` 은 그대로 두었습니다 — 토크를 켜고 나서 상태를 받는 편이
> 순서상 자연스럽고 해도 해롭지 않기 때문이지, 이 절이 말한 이유 때문이 아닙니다.
>
> **왜 이렇게 헷갈렸나:** 전원이 꺼진 상태에서 다시 켰을 때 0/6과 2/6이 갈렸는데, 그 갈림은
> 전원이 아니라 2 ms 창의 타이밍이었습니다. 두 변인이 같은 순간에 바뀌어서 잘못된 쪽에
> 원인을 붙였습니다.

## 0c. 크리티컬 — 모터 전원을 켜기 전에 각도를 물어봅니다 (재시작할 때마다 멈춤)

### 쉬운 말로

`ControlLoop` 은 **모터 전원을 loop 안에서** 켭니다(`_enter()` -> `robot.enable()`). 그런데 각도를
모르는 모터에는 명령을 보내지 않는 안전 규칙(0.5절 `NO_STATE`)이 있고, MIT 방식에는 **명령을 보내야만
각도가 돌아오는** 구조라서, loop 이 시작되기 전에 각도를 한 번 받아두어야 합니다.

문제는 **전원이 꺼진 모터는 명령 프레임에 아예 응답하지 않는다**는 점입니다. 그래서 "각도를 먼저
물어보고 그 다음 전원" 순서면 영원히 답을 못 받고, 아무 명령도 나가지 않는 상태로 굳습니다.

### 증상 (실측, 2026-09-05)

정상 종료(`_exit()` 가 토크를 끊음) 직후 다시 켜면:

```
[remote_motion] seeded measured positions on left_leg: 0/6 motors answered
통신선로 송신 3초간 +0 건        <- 100 Hz 로 돈다면서 한 건도 안 나감
stats: ... idle_refresh=19027    <- 루프는 멀쩡히 돌고 있음
```

## 0d. 크리티컬 — 상태를 받는 창이 2 ms 로 고정이라, 일부만 꽂힌 장비에서 실패합니다

### 쉬운 말로

`refresh_states()` 는 "모터들아 지금 각도가 몇이냐" 하고 물어본 뒤 **2 ms 동안만** 답을 기다립니다.
그리고 **선언된 모터 수만큼** 답이 와야 일찍 빠져나옵니다. 벤치처럼 6개를 선언하고 2개만 꽂혀 있으면
6개는 절대 안 채워지므로 **항상 2 ms 를 다 씁니다.**

1 Mbit/s 에서 명령 6개 + 응답 2개는 약 0.9 ms 입니다. 2 ms 안에 들어가긴 하지만 **아슬아슬**해서,
그날의 스케줄링에 따라 응답이 창 안에 들어오기도 하고 못 들어오기도 합니다.

### 증상 (실측, 2026-09-05)

같은 코드, 같은 장비, 연속된 두 번의 시작:

```
[remote_motion] seeded measured positions on left_leg: 2/6 motors answered   <- 성공
[remote_motion] seeded measured positions on left_leg: 0/6 motors answered   <- 실패
```

**0/6 은 회복되지 않습니다.** 각도를 모르면 0.5절의 `NO_STATE` 가 모든 명령을 막고, 명령이 안 나가면
응답도 없어 영영 각도를 모릅니다. 화면에는 100 Hz 로 멀쩡히 도는 것처럼 보이고 모터만 죽어 있습니다.

원인을 여기로 좁힌 근거: **모터 2개를 2개로 선언한** 같은 버스에서는 같은 호출이 한 번도 실패하지
않았습니다(6회 연속 성공). 즉 모터가 아니라 기다리는 창이 문제입니다.

### 위치

```python

...

    ...

```

### 수정안

기다리는 시간을 부르는 쪽이 정할 수 있게 하고, 기본값도 올립니다.

```python

## 1. 크리티컬 — 고장값을 반대 순서로 읽습니다

### 쉬운 말로

모터가 "나 고장났어, 이유는 이거야"라고 숫자를 보내는데, 그 숫자를 **거꾸로 읽고** 있었습니다.
그래서 "전압이 너무 높다"라는 흔하고 명확한 고장이, 설명서에 없는 정체불명의 숫자로 보였습니다.
멈춘 이유를 알 수 없으니 엉뚱한 곳을 찾게 됩니다. 실제로 저희가 그랬습니다.

### 위치

`src/huphy/motors/robstride/codec/mit.py::decode_fault` (148행)

### 증상

2026-09-05 벤치에서 모터 2대가 동시에 멈췄습니다. 고장 조회 결과가 `0x08000000` — **비트 27**인데
설명서에는 그런 고장이 없습니다(정의된 것은 0·1·2·3·7·14번뿐). 같은 바이트를 반대로 읽으면
`0x00000008` = **비트 3 = 과전압**입니다.

### 왜 그런가

이 제조사는 프레임 종류마다 바이트 순서가 다릅니다.

- **상태 프레임**(위치·속도·토크·온도)은 큰 자리부터입니다. `decode_state`가 맞게 읽고 있고,
  제조사 SDK도 같습니다(`struct.unpack('>H', ...)`).
- **고장 프레임**은 작은 자리부터입니다. 제조사 공식 SDK가 같은 프레임을 이렇게 읽습니다:

  ```python
  # robstride_dynamics/bus.py
  fault_value, warning_value = struct.unpack("<LL", data)   # "<" = 작은 자리 먼저
  ```

  설명서(통신 타입 21) 표도 같습니다: `Byte0~3 고장값 / Byte4~7 경고값`.

우리가 쓰는 통신 방식(11비트 프레임)에서는 맨 앞 바이트가 모터 번호라 설명서 대비 한 칸 밀립니다.
실측 응답이 그걸 보여줍니다.

```
RS03 (번호 3) : 03 00 00 00 00
RS04 (번호 4) : 04 00 00 00 00 00 00 00
                ^^ 모터 번호   ^^^^^^^^^^^ 고장값(4바이트, 작은 자리 먼저)
```

**밀리는 것은 위치일 뿐 순서가 아닙니다.**

### 수정안

```python
# 전
word = (data[1] << 24) | (data[2] << 16) | (data[3] << 8) | data[4]

# 후
word = int.from_bytes(data[1:5], "little")
```

`fix-fault-byte-order` 가지 커밋 `e9ddfe8`에 반영했습니다. 시험 3곳이 옛 순서를 전제로 프레임을
만들고 있어 함께 고쳤고, 벤치에서 실제로 받은 바이트를 재현 시험으로 박아 두었습니다.
시험 전체 1,074건 통과.

### 덧붙임 — 경고값은 이 통신 방식에서는 오지 않습니다 (2026-09-05 실측)

설명서에는 고장값 뒤에 **경고값**이 따라온다고 되어 있습니다(비트 0 = 과열 경고, 기본 135도).
과열은 고장(145도)이 나기 전에 경고(135도)가 먼저 뜨므로 **타기 전에** 알 수 있어 쓸모가 큽니다.

그런데 **우리가 쓰는 11비트 통신에서는 오지 않았습니다.** 실측 응답이 그걸 보여줍니다.

```
RS03 (번호 3) : 03 00 00 00 00               (5바이트)
RS04 (번호 4) : 04 00 00 00 00 00 00 00       (8바이트)
                ^^ 모터 번호
                   ^^^^^^^^^^^ 고장값 4바이트
                               ^^^^^^^^^^^ 경고값 자리인데 RS03에는 아예 없고 RS04도 0
```

설명서의 경고값은 29비트 통신 기준이고, 거기서는 모터 번호가 CAN 주소에 들어가 데이터 8바이트를
고장 4 + 경고 4로 온전히 씁니다. 11비트 통신은 첫 바이트를 모터 번호가 차지해 자리가 모자랍니다.

**확인이 필요한 것**: 11비트 통신에서 경고값을 얻을 다른 방법이 있는지(별도 조회 명령이나 파라미터
읽기 0x3022 계열). 있으면 과열을 미리 잡을 수 있습니다.

## 2. 버그 — 고장이 나도 어디에도 실리지 않습니다

### 쉬운 말로

보이는데 값만 얼어붙습니다.** 저희는 3분 동안 "잘 돌고 있다"고 믿으며 아무 일도 일어나지 않는
데이터를 기록했습니다.

### 위치

`src/huphy/telemetry/snapshot.py` — 내보내는 항목에 고장이 없습니다.
현재 모터별 항목: `pos tgt err vel tau`(빠른 묶음), `temp age ack miss`(진단 묶음).

### 증상 (실측)

```

응답     ack=1, miss=0                         ← 정상으로 보임
값       무릎 각도 141.40도로 170초간 고정     ← 실제로는 멈춰 있었음

고장을 지우자 온도가 34.0도로 정상 복귀했습니다. 즉 **고장 상태에서 읽은 값은 믿을 수 없는데,
그걸 구분할 방법이 없습니다.**

### 수정안

진단 묶음에 고장·경고를 추가하는 것이 가장 간단합니다.

```python
# telemetry/snapshot.py
DIAG_MOTOR_FIELDS = ("temp", "age", "ack", "miss", "fault", "warn")
```

다만 **고장 조회를 제어 주기 안에서 하면 위험합니다.** 고장 응답은 상태 응답과 CAN 번호가 같아,
제어 루프가 그걸 상태로 잘못 읽을 수 있습니다(위 온도 3308.8도가 그런 경우로 보입니다).
안전한 방법 두 가지를 제안합니다.

1. 상태 프레임 자체에 실린 상태 비트를 쓰는 방법. 제조사 SDK는 29비트 통신에서 **CAN 주소 안**에
   상태 비트가 있다고 적고 있습니다(과열·과전류·저전압·스톨·인코더). 11비트 통신에서도 같은 정보를
   얻을 수 있는지 확인해 볼 가치가 있습니다 — 그러면 **추가 프레임 없이** 매 주기 알 수 있습니다.
   ```python
   # robstride_dynamics/bus.py — 참고용
   status_stall            = (extra_data >> 12) & 0x01
   status_overtemperature  = (extra_data >> 10) & 0x01
   status_overcurrent      = (extra_data >>  9) & 0x01
   status_undervoltage     = (extra_data >>  8) & 0x01
   ```
2. 그게 안 되면, 낮은 주기(예: 1초에 한 번)로 고장을 조회하되 **응답을 상태로 오인하지 않도록**
   조회 직후의 첫 응답만 고장으로 처리하고 나머지는 버리는 규칙을 명시적으로 두는 방법.

## 5b. 크리티컬 — 상태를 모르면 명령을 거부하는데, 상태는 명령으로만 옵니다 (스스로 갇힘)

### 쉬운 말로

로봇은 "지금 어디 있는지 모르는 관절"에는 명령을 보내지 않습니다. 안전을 위해 옳은 규칙입니다.
그런데 **현재 위치는 명령을 보내야만 돌아옵니다.** 그래서 한 번 위치를 잃으면
`명령 없음 → 응답 없음 → 위치 모름`으로 스스로 갇혀 영영 빠져나오지 못합니다.

### 위치

`src/huphy/safety/guards.py:133` — `current_deg is None` 이면 `RejectReason.NO_STATE` 로 거부
`src/huphy/robots/leg.py:487` — 거부된 모터는 건너뜀
`src/huphy/control/loop.py:268` — 제어 모드에서는 `refresh()` 를 부르지 않음

### 증상 (실측, 2026-09-05)

겉보기 지표가 전부 정상이라 알아채기 어렵습니다.

```
제어 루프  1500주기 15.0초, 평균 100.0Hz, 밀림 0회, "무응답 주기 0회"   ← 완벽해 보임
와이어     위치 명령 프레임이 하나도 나가지 않음
로봇 보고  ack = -1 (명령한 적 없음), age = -1
화면       두 관절 모두 각도 0.0, 상태 '죽음'
```

"무응답 0회"인 이유는 **보낸 것이 없어 받을 것도 없었기** 때문입니다. 지표가 거짓말을 합니다.

### 우리가 쓰는 우회

제어 루프를 시작하기 전에 `bus.refresh_states()` 를 **한 번** 부릅니다. 이건 전 게인 0짜리
프레임이라 힘이 걸리지 않으면서 모터가 자기 상태를 답하게 만듭니다. 한 번이면 갇힘이 풀리고,
그다음부터는 각 명령의 응답이 상태를 계속 갱신합니다.

```python
# 우리 쪽 bridge/huphy_remote_motion.py, 제어 루프 시작 전
missing = bus_obj.refresh_states()
# 실측 출력: "seeded measured positions on left_leg: 2/6 motors answered (no answer: [1, 2, 5, 6])"
```

### 제안

`ControlLoop._enter` 에서 제어 모드로 들어갈 때 **한 번** 상태를 읽어 주면 이 갇힘이 원천적으로
사라집니다. 또는 `guards.apply` 가 `NO_STATE` 로 거부한 사실이 어딘가에 드러나면(지금은 조용히
건너뜀) 최소한 원인을 알 수 있습니다. 지금은 "완벽하게 도는 루프"로 보입니다.

## 5c. 참고 — 관측값 이름이 통신 항목 이름과 다릅니다 (우리가 겪은 함정)

로봇 라이브러리가 내주는 관측값의 이름과, 통신으로 나가는 항목 이름이 **한 군데에서 다릅니다.**

| 항목 | 관측값 이름 (`Leg.get_observation`, `robots/leg.py:364-367`) | 통신 항목 이름 (`telemetry/snapshot.py`) |
|---|---|---|
| 위치 | `.pos` | `pos` |
| 속도 | `.vel` | `vel` |
| 토크 | **`.torque`** | **`tau`** |
| 온도 | `.temp` | `temp` |

우리가 통신 쪽 이름(`tau`)을 관측값에도 쓰는 줄 알고 `.tau`를 읽었더니 **늘 비어** 있었고,
"값이 없으면 판정하지 않는다"는 우리 쪽 안전 규칙 때문에 **과전압으로 170초간 멈춰 있던 무릎을
한 번도 '멈춤'으로 보고하지 못했습니다.** 조용히 실패하는 종류라 찾기 어려웠습니다.

버그는 아니고 우리 착각이지만, 같은 함정을 다음 사람도 밟습니다. 두 이름을 맞추거나, 최소한
한 곳에 나란히 적어 두면 좋겠습니다.
