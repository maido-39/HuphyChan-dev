# 124. HUPHY 개발자에게 넘기는 발견 목록

> **이 문서는 HUPHY를 만드는 사람에게 그대로 건네려고 쓴 것입니다.** 우리(뷰어·원격조작 쪽)가
> 실물 모터 2대를 붙여 쓰면서 찾은 것들을 모았습니다. 쉬운 말로 씁니다 — 우리끼리 만든 줄임말을
> 쓰지 않습니다.
>
> **이 문서가 HUPHY 관련 발견을 적는 유일한 곳입니다** (사용자 지시 2026-09-05). 버그, 구현 오류,
> 우리에게 필요한 것 — 무엇을 새로 찾든 새 문서를 만들지 말고 여기에 항목을 덧붙이고 갱신합니다.
> 그래야 개발자가 한 곳만 보면 됩니다.
>
> 확인 환경: 벤치 10.8.0.14, `can0`(CANable를 slcand로 올림, 1 Mbps), 모터 2대
> — 엉덩이 회전(RS03, 번호 3), 무릎(RS04, 번호 4). HUPHY `biped` 가지(`cd6b8ac`) 기준.
> 참고 자료: `Motor_Spec/manuals/RS03_User_Manual_251112.pdf`, `RS04_User_Manual_251112.pdf`
> (제조사 배포본에서 받음), 제조사 공식 SDK
> `ROBSTRIDE-DYNAMICS/Robstride-Dynamics-Python-SDK`.
>
> **HUPHY 원본 가지는 건드리지 않았습니다.** 고친 것은 새 가지에만 있습니다:
> `fix-fault-byte-order`(커밋 `e9ddfe8`), `bench-partial-rig`(벤치 설정).

## 1. 크리티컬 — 고장값을 반대 순서로 읽습니다

### 쉬운 말로

모터가 "나 고장났어, 이유는 이거야"라고 숫자를 보내는데, 그 숫자를 **거꾸로 읽고** 있었습니다.
그래서 "전압이 너무 높다"라는 흔하고 명확한 고장이, 설명서에 없는 정체불명의 숫자로 보였습니다.
멈춘 이유를 알 수 없으니 엉뚱한 곳을 찾게 됩니다. 실제로 저희가 그랬습니다.

### 위치

`src/huphy/motors/robstride/codec/mit.py::decode_fault` (148행)

### 증상

2026-09-05 벤치에서 모터 2대가 동시에 멈췄습니다. 고장 조회 결과가 `0x08000000` — **비트 27**인데
설명서에는 그런 고장이 없습니다(정의된 것은 0·1·2·3·7·14번뿐). 같은 바이트를 반대로 읽으면
`0x00000008` = **비트 3 = 과전압**입니다.

### 왜 그런가

이 제조사는 프레임 종류마다 바이트 순서가 다릅니다.

- **상태 프레임**(위치·속도·토크·온도)은 큰 자리부터입니다. `decode_state`가 맞게 읽고 있고,
  제조사 SDK도 같습니다(`struct.unpack('>H', ...)`).
- **고장 프레임**은 작은 자리부터입니다. 제조사 공식 SDK가 같은 프레임을 이렇게 읽습니다:

  ```python
  # robstride_dynamics/bus.py
  fault_value, warning_value = struct.unpack("<LL", data)   # "<" = 작은 자리 먼저
  ```

  설명서(통신 타입 21) 표도 같습니다: `Byte0~3 고장값 / Byte4~7 경고값`.

우리가 쓰는 통신 방식(11비트 프레임)에서는 맨 앞 바이트가 모터 번호라 설명서 대비 한 칸 밀립니다.
실측 응답이 그걸 보여줍니다.

```
RS03 (번호 3) : 03 00 00 00 00
RS04 (번호 4) : 04 00 00 00 00 00 00 00
                ^^ 모터 번호   ^^^^^^^^^^^ 고장값(4바이트, 작은 자리 먼저)
```

**밀리는 것은 위치일 뿐 순서가 아닙니다.**

### 수정안

```python
# 전
word = (data[1] << 24) | (data[2] << 16) | (data[3] << 8) | data[4]

# 후
word = int.from_bytes(data[1:5], "little")
```

`fix-fault-byte-order` 가지 커밋 `e9ddfe8`에 반영했습니다. 시험 3곳이 옛 순서를 전제로 프레임을
만들고 있어 함께 고쳤고, 벤치에서 실제로 받은 바이트를 재현 시험으로 박아 두었습니다.
시험 전체 1,074건 통과.

### 덧붙임 — 경고값도 있습니다

설명서에 따르면 고장값 뒤에 **경고값**이 따라옵니다(비트 0 = 과열 경고, 기본 135도). 지금은 읽지
않습니다. 과열은 고장(145도)이 나기 전에 경고(135도)가 먼저 뜨므로, 이걸 읽으면 **타기 전에**
알 수 있습니다.

## 2. 버그 — 고장이 나도 어디에도 실리지 않습니다

### 쉬운 말로

모터가 고장으로 힘을 끊어도, 통신은 멀쩡하고 모터도 대답합니다. 그래서 **화면에는 "정상"으로
보이는데 값만 얼어붙습니다.** 저희는 3분 동안 "잘 돌고 있다"고 믿으며 아무 일도 일어나지 않는
데이터를 기록했습니다.

### 위치

`src/huphy/telemetry/snapshot.py` — 내보내는 항목에 고장이 없습니다.
현재 모터별 항목: `pos tgt err vel tau`(빠른 묶음), `temp age ack miss`(진단 묶음).

### 증상 (실측)

```
통신     초당 110회, 마지막 수신 0.006초 전    ← 정상으로 보임
응답     ack=1, miss=0                         ← 정상으로 보임
값       무릎 각도 141.40도로 170초간 고정     ← 실제로는 멈춰 있었음
온도     3308.8도                              ← 깨진 값
```

고장을 지우자 온도가 34.0도로 정상 복귀했습니다. 즉 **고장 상태에서 읽은 값은 믿을 수 없는데,
그걸 구분할 방법이 없습니다.**

### 수정안

진단 묶음에 고장·경고를 추가하는 것이 가장 간단합니다.

```python
# telemetry/snapshot.py
DIAG_MOTOR_FIELDS = ("temp", "age", "ack", "miss", "fault", "warn")
```

다만 **고장 조회를 제어 주기 안에서 하면 위험합니다.** 고장 응답은 상태 응답과 CAN 번호가 같아,
제어 루프가 그걸 상태로 잘못 읽을 수 있습니다(위 온도 3308.8도가 그런 경우로 보입니다).
안전한 방법 두 가지를 제안합니다.

1. 상태 프레임 자체에 실린 상태 비트를 쓰는 방법. 제조사 SDK는 29비트 통신에서 **CAN 주소 안**에
   상태 비트가 있다고 적고 있습니다(과열·과전류·저전압·스톨·인코더). 11비트 통신에서도 같은 정보를
   얻을 수 있는지 확인해 볼 가치가 있습니다 — 그러면 **추가 프레임 없이** 매 주기 알 수 있습니다.
   ```python
   # robstride_dynamics/bus.py — 참고용
   status_stall            = (extra_data >> 12) & 0x01
   status_overtemperature  = (extra_data >> 10) & 0x01
   status_overcurrent      = (extra_data >>  9) & 0x01
   status_undervoltage     = (extra_data >>  8) & 0x01
   ```
2. 그게 안 되면, 낮은 주기(예: 1초에 한 번)로 고장을 조회하되 **응답을 상태로 오인하지 않도록**
   조회 직후의 첫 응답만 고장으로 처리하고 나머지는 버리는 규칙을 명시적으로 두는 방법.

## 3. 버그 — 화면 출력이 파일로 갈 때 안 보입니다

### 쉬운 말로

프로그램을 파일로 기록하며 돌리면 **시작 알림조차 안 보입니다.** 파이썬이 글을 모아 뒀다가
나중에 한꺼번에 쓰기 때문입니다. 그래서 "떴는지 안 떴는지" 알 수 없어 시간을 버렸습니다.

### 위치

`src/huphy/scripts/` 전반의 `print(...)`

### 증상

로그 파일에 CAN 연결 줄만 있고 시작 알림이 없어 프로그램이 죽은 줄 알았습니다. 실제로는 살아
있었고, 종료하자 그제야 모아 둔 글이 한꺼번에 나왔습니다.

### 수정안

```python
print(..., flush=True)
```
또는 진입점에서 한 번만:
```python
sys.stdout.reconfigure(line_buffering=True)
```

## 4. 우리에게 필요 — 부분만 조립된 로봇을 만들 수 없습니다

### 쉬운 말로

다리 하나에 모터가 6개 다 있어야만 로봇을 만들 수 있습니다. 저희 책상에는 2개뿐이라 만들 수가
없었습니다. **지금은 설정에 6개를 다 적고 없는 4개는 응답이 없게 두는 방식으로 우회**하고 있습니다.
동작은 하지만 없는 모터가 계속 "죽었다"고 표시됩니다.

### 위치

`src/huphy/robots/leg.py:84` `REQUIRED_MOTORS`, `:168` 검사
조립 함수는 `build_leg`, `build_biped` 둘뿐이고 `build_biped`는 `kind: leg`만 모읍니다.

### 왜 지금은 급하지 않은가

우회가 됩니다. 다만 두 가지를 함께 낮춰야 합니다(저희 벤치 설정 `config/robot_bench.yaml`,
`bench-partial-rig` 가지):

```yaml
link_loss_cycles: 0     # 없는 모터 4개가 매 주기 응답을 빠뜨려 "통신 끊김"으로 판정됨
enforce_limits: false   # 캘리브레이션이 비어 있어 enable()이 거부됨
```

**기본값을 유지하는 것에 찬성합니다** — 6개를 요구하는 것은 실기에서 옳은 안전장치입니다.
필요하다면 명시적으로 켜는 부분 조립 방식(예: `allow_partial=True`)이면 충분합니다.

## 5. 우리에게 필요 — 명령을 보내야만 상태를 읽습니다

### 쉬운 말로

로봇을 **가만히 두고 관절 각도만 보고 싶을 때**, 명령을 안 보내면 아무 값도 안 옵니다.
힘을 주지 않고 보기만 하는 상황(사람이 손으로 움직이는 걸 화면에 그리기)이 그대로는 안 됩니다.

### 위치

`src/huphy/control/loop.py::step` (257~275행)

```python
if self.mode is Mode.OBSERVE:
    missing = self.robot.refresh()      # 여기서만 상태를 읽음
else:
    action = motion(t, observation) if motion is not None else None
    if action:
        self.robot.send(self.robot.build_commands(action))
    missing = self.robot.collect()      # 보낸 명령의 응답만 받음
```

제어 방식에는 "읽기 전용 명령"이 없어서 생기는 구조적 성질이지 버그는 아닙니다. 다만 제어 모드에
있으면서 아직 아무것도 명령하고 싶지 않을 때 상태가 영영 0으로 남습니다.

### 우리가 쓰는 우회

명령이 없을 때 **세기 0짜리 명령**을 보냅니다. 힘은 전혀 걸리지 않고 모터는 대답하므로 값이
들어옵니다. `refresh_states()`가 하는 일과 같은 원리입니다.

### 제안

제어 모드에서도 명령이 없으면 `refresh()`를 부르는 선택지가 있으면 저희 우회가 필요 없습니다.

## 6. 참고 — 확인된 온도·전압 기준 (설명서)

RS03·RS04 동일합니다.

| 항목 | 값 |
|---|---|
| 사용 온도 범위 | −20 ~ 50도 |
| 권선 한계 온도 | 130도 |
| 과열 고장 | 145도 |
| 과열 경고 | 135도 |
| 과전압 고장 | 보호 전압 + 60V 초과 |
| 저전압 고장 | 12V 미만 |

저희는 사용자 지시로 **50도에서 힘을 끊고 45도 아래에서 다시 시작**하는 규칙을 저희 쪽에 넣을
예정입니다(사용 온도 상한과 같습니다).
