시나리오 전환 UI — 3안 비교 목업

클릭 가능한 목업 3개. 순수 프론트엔드이며 서버 호출 없음 — 상태는 페이지 안에서만 가짜로 계산된다. 실제 대시보드(/, /dash)는 이 페이지들과 무관하게 그대로 동작한다.

공통 설계 원칙 — 세 조합은 뷰어가 소유한 새 상태가 아니라, 이미 존재하는 상태 (mode + TX 무장 + 로봇 프로그램 확인)에서 계산되는 이름이다. 버튼은 그 조합으로 점프하는 스위치일 뿐 눌린 채로 남지 않으며, 세 축이 정확히 맞지 않으면 이름은 언제나 custom으로 떨어지고 어긋난 항목을 지목한다. 로봇 쪽 확인 상태는 3단계 (확인됨/모름/불일치)로 표시해 "화면 표시와 실제 로봇 상태가 어긋날 수 있음"을 숨기지 않는다.

안 C

TX 패널 "운용 모드" 카드

전송이 실제로 걸린 유일한 축(TX 패널) 안에서 조합을 고른다. 위험한 전환(실물 동시 구동)에 해제→설정→ARM 절차를 강제해 세 안 중 가장 마찰이 크다. 대신 전송과 무관한 두 조합까지 TX 패널에 들어와 위치가 어색하고 패널이 길어진다.

선택 기준

  • 정직성 — custom·불가·로봇 확인상태(모름/불일치)를 상시 보이는 자리에 담을 수 있는가. B > C > A.
  • 위험 마찰 — 실물 동시 구동(토크 ON) 전환이 실수로 일어나기 얼마나 어려운가. C(해제→설정→ARM 강제) > B(축별 확인모달) > A(같은 줄의 버튼 하나, 모달은 있지만 다른 두 버튼과 시각적으로 제일 안 떨어져 있음).
  • 도달 비용 — 전환에 필요한 클릭 수. A < C < B.
  • 구현 비용 — 기존 상단바/좌측탭/TX패널 중 무엇을 얼마나 건드리는가. A가 가장 작고, B는 새 탭+체크리스트 로직, C는 TX 패널 리팩터가 가장 크다.
  • 로봇 전환 이행 경로(2번→1번) — 세 안 모두 "안내만" 토글로 동일 구조를 이미 갖고 있어, 기본값만 바꾸면 자동 SSH → 안내 전용으로 이행 가능함을 목업에서 확인.

검증 메모

이 호스트에는 브라우저가 없어 실제 렌더링/클릭 동작은 육안으로 확인하지 못했다. HTML/JS 구문 검사와 curl 서빙 확인(200, 파일 바이트 일치)만 거쳤다 — 사용자가 브라우저로 열어 직접 클릭해봐야 최종 확인이 끝난다.
